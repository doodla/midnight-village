# Backend tests

`just test` runs pytest (built from the models, `--nomigrations`) and then the migration
tests in a second pass (`just test-migrations`). `just test tests/path/test_x.py` runs one
file (first pass only). Conventions: descriptive names, every random choice seeded,
multi-player scenarios. Coverage minimum 80% (`pyproject.toml`).

## Side effects after commit, and timers in tests

Every WebSocket send and `timers.schedule` / `cancel` in the night flow goes through `transaction.on_commit` (`_send_after_commit`, `_schedule_after_commit`, `_cancel_after_commit`), so a rollback leaves nothing sent or rescheduled. Tests that call these services inside pytest's transaction must use `django_capture_on_commit_callbacks(execute=True)` (or `django_db(transaction=True)`). The autouse fixture makes `timers.schedule` a no-op; `make_night` (`tests/onuw/conftest.py`) records `(key, delay, callback)` instead, where calling the callback runs the job; tests that need real rows/threads use `@pytest.mark.uses_timers` and, for the queue backend, `timers.set_queue_sender(fake)` + `queue_worker.handle_message(payload)`. A test with real memory-backend threads waits for the thread itself (`tests/timer_threads.py`: `settle(key)` follows re-arms, `join(thread)` for one already cancelled or replaced), never a fixed sleep and never the job's side effect: the job runs inside the transaction that claims and deletes the row, so its effect shows before that deletion commits. A timer the test must cancel or replace first is scheduled far off (an hour), so a slow machine cannot fire it before the test gets there; due times are written with the database clock (`Now()`).

## Traps

- **WebSocket connections require JWT auth.** The ASGI middleware validates tokens. Tests need `WebsocketCommunicator` with an authenticated user scope — unauthenticated connections are rejected silently.

- **Throttle rates must be configured in test settings.** Guest auth endpoints use DRF throttling. If `DEFAULT_THROTTLE_RATES` is missing from test settings, guest creation tests fail with 429s that look like server errors.

## Migration tests

`tests/test_migrations.py` (marker `migration`) applies the REAL migrations (the rest of the suite uses `--nomigrations`, where these tests skip), seeds old-shape rows through the historical models, migrates forward, asserts, runs the old code's INSERTs (`tests/old_code.py`, never add columns to them), then back and forward again. Add a case per migration. `tests/test_migration_rules.py` scans every migration file for app imports and the `lock_timeout` first operation. The rules themselves: `docs/dev/deploy-vercel.md`, "Deploy-safe changes".

## Contract samples (`tests/contract/`)

`tests/contract/` records what the server sends, for the app's tests: `scenarios.py` first plays three tables made without `defaults` (no look stage): a classic six-player game with the default timers (sign-in, lobby set-up and every lobby event, the deal and its refusals, the night closed by the harness's timer hook, the talk, a vote with a Hunter chain, "where am I" in every state, the night results ack, recent games and online stats, most error bodies); an untimed eight-player game with a Doppelganger (window 1, the host closing window 2, host handover, the host's reveal with abstentions, the night timeline, the oracle), then a second game there by play again (she copies a Werewolf; a dealt Tanner dies); a full ten-player table for the join refusals through the real API (`recorder.Table`: DRF test client against the URL conf; a `RecordingLayer` channel layer whose group messages are turned into client frames by the consumers' own handlers; on-commit effects run per request; real timer rows with no thread, `is_scheduled` = the row exists, fired by claiming the row; clock frozen at a past date, user ids from 1, fixed lobby codes and forced-deal seed; game ids, guest usernames and tokens replaced by stable stand-ins). Each socket sample's index entry has `group` (`player` or `broadcast`) and `recipients`; `test_contract_privacy.py` fails if any per-player night event is recorded at all, or a game broadcast before the results names a role. `test_contract_samples.py` writes them to `contract_samples/` at the repo root with `UPDATE_CONTRACT_SAMPLES=1` (`just samples`) and otherwise fails, with a diff, if the committed files differ. A new endpoint, event or situation is a `table.record(...)` / `table.record_event(...)` line in `scenarios.py`, then `just samples`. A payload change shows up as a diff of the samples (review it), and may fail the app's tests where a fixture relied on the old shape.

**The choose tables.** `scenarios.choose_tables` (after the three tables above) plays four more tables: a plain five-player table made with `defaults: "v2"` (the look stage with `ready` / `progress`, window 2 where every phone with a choice chooses once (the Villager's choose is still recorded, taken alike), the lone Werewolf's prompt, every `choose` answer and refusal, ready to vote, the lock-in vote with pick / re-pick / lock / 409, the oracle), a nine-player Doppelganger table with a real Werewolf pack (window 1 with her two chooses and a stale-stage refusal, her look listed at once, then window 2 and every prompt kind; the recorder sends each request's current `stage` unless a scenario names a stale one), and the automatic deck at 5 (classic) and 9 (chaos) players; the five-player game's `/results/` is recorded too (`results_five`, the playtest pack's game 7). `scenarios.results_tables` then plays three more: six players played to the results by play again (the Werewolves win, nobody dies, a tie that kills two, the Hunter chain, the Tanner, a dead Robber who held a Werewolf card; the night results ack in the talk; a Doppelganger who copied the Minion with her follow-up armed), a three-player game with an untimed talk and vote, and a ten-player talk and vote; then a table before its deal (`_lobby_table`): lobby sockets (`Table.connect_lobby` / `disconnect_lobby`), a phone that drops (in its grace period, then told when the presence check fires) and comes back, `deck_preview` for each chip at four and seven players, `deal` for a custom deck that fits and one a card short, a join of another table refused because the player sits at this waiting one, and a deal nobody tapped ready for. Every request to a stage endpoint is sent the way the app sends it: the recorder adds the game's current `stage` (and, for a `choose`, the prompt's `chosen`) unless the scenario names one. `Table.record_sequence` stores per seat the TYPES of the game events heard in a window (`ws_sequence/*`); the privacy test requires them equal for every seat and free of player-only night events, and every `night_window` / `progress` sample to be a broadcast. A diff in any sample is a behaviour change: review it, and fix the server if it was not meant.
