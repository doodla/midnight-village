# Backend — Midnight Village

## ONUW Game Domain

Understand these mechanics before implementing any game feature.

**Game flow:** Lobby → Night → Discussion → Voting → Results

**Night phase runs in two windows** (`Game.current_wave` holds the window number: 1 or 2, 0 outside night). `RoleDefinition.wave` is the *order group* (position in the wake order), not a phase of the game; action-log entries are tagged with it so the log stays in wake order.
1. **Window 1 — Doppelganger alone.** Runs whenever the Doppelganger card is in the deck (dealt or in the center), even if nobody can act. It lasts **exactly** `night_doppelganger_window_seconds` (default 10) whatever happens in it (nobody to act, look submitted or not, follow-up or not): one timer is set when it opens, nothing reschedules it, and `phase_deadline` is the real close time. `0` turns the fixed length off: window 1 then closes like window 2. The look resolves and is sent on submit; a follow-up as Seer/Robber/Troublemaker/Drunk/Minion is prompted on submit but resolves when the window closes; anything unsubmitted is skipped.
2. **Window 2 — everyone else at once.** Always runs, even if nobody has a choice. Every actor is prompted together: dealt Werewolves, Minion, Masons, Seer, Robber, Troublemaker, Drunk, Insomniac, and a Doppelganger who copied Werewolf/Mason/Insomniac. Nothing is sent to anyone until the window closes; then the engine resolves, each step seeing the table after the previous one: team views (group 2), Seer -> Robber -> Troublemaker -> Drunk (group 3, Doppelganger before the real role), Insomniac (group 4). Engine entry points: `get_required_actions_for_window`, `resolve_window` (`resolve_night` still takes actions keyed by order group 1-4).
- **Timing (window 2):** a window closes when its last actor submits, but never sooner than `night_min_window_seconds` (default 8) after it opened (the close is scheduled for that moment); `night_wave_seconds` (default 30) is the maximum. Host "advance" closes any window immediately. Timer settings (`night_wave_seconds`, `night_min_window_seconds`, `night_doppelganger_window_seconds`, `discussion_seconds`, `voting_seconds`; and `disconnect_grace_seconds`, 0-60; `host_handover_seconds`, 0-600) are validated in `validate_onuw_settings` (integers 0-3600; min window <= `night_wave_seconds` when that is > 0); `get_timer_seconds` falls back to the default on a bad stored value.
- **Side effects after commit:** every WebSocket send and `timers.schedule/cancel` in the night flow goes through `transaction.on_commit` (`_send_after_commit`, `_schedule_after_commit`, `_cancel_after_commit`), so a rollback leaves nothing sent or rescheduled. Payloads are built inside the transaction. Tests that call these services inside pytest's transaction must use `django_capture_on_commit_callbacks(execute=True)` (or `django_db(transaction=True)`). Job exceptions are logged by `make_idempotent_callback`. Tests: the autouse fixture makes `timers.schedule` a no-op; `make_night` (tests/onuw/conftest.py) records `(key, delay, callback)` instead, where calling the callback runs the job; tests that need real rows/threads use `@pytest.mark.uses_timers` and, for the queue backend, `timers.set_queue_sender(fake)` + `queue_worker.handle_message(payload)`.
- **Dealt-card rule:** who wakes as a Werewolf or Mason, who acts in every step, and who a Minion sees is decided by the card DEALT (`state.original_roles`) plus a Doppelganger who copied that role, never the card held mid-night. A stolen Werewolf card does not make the thief a Werewolf; the player it was taken from still wakes (and can be the "lone" Werewolf). Winning is still decided by the card held at the end.
- **Drunk never skips.** A Drunk (or a Doppelganger who copied the Drunk) who runs out of time, or is gone past the grace period, is swapped by the server (`services._timeout_action`): center index from `drunk_timeout_center_index(random_seed, player_id, 3)` (a dedicated `random.Random` seeded from the game seed, the label `drunk-timeout` and the player id), resolved when the window closes like a chosen swap, same result sent (`{"card_index"}`), logged as a normal `swap_with_center` entry with `"made_by_server": true`. The prompt offers only `swap_with_center`; a `skip` is refused.
- **Results** are stored per window (`night_action_data["wave_<window>_result"]`); a player gets at most one in window 2.

## Restart, play again, dropped phones, missed results

**How many server processes?** Depends on `ONUW_TIMER_BACKEND`. With `"vercel_queue"` (Vercel; `config/settings/vercel.py`) there is NO per-process state: timers are rows fired by queue messages, presence is rows with heartbeats, nothing resets or re-arms at start-up, so any number of instances may start and stop at any time (`docs/dev/deploy-vercel.md`). With `"memory"` (default: dev, tests, harness, `just dev`) still run ONE process: its timers are `threading.Timer`s in that process (the rows make them survive a restart, but a timer armed in process A is lost with A until a restart re-arms it, and a second process would not know about A's timers), and `recover_timers` re-derives and re-arms at start-up. Redis in `production.py` is only the channel layer. Recovery logs one INFO line about it at every start. (The repo has no Dockerfile or Procfile: `just dev`/`just serve`/`just harness-serve` and CI.)

**Where things live (principle 6).** `apps.core` is shared infrastructure and imports NO game app (a test scans its source): lobbies, `LobbySocket` rows and the lobby consumer, host handover (`core/host.py`), play again (`core/lobbies.py`), the after-commit helpers (`core/effects.py`), durable timers (`core/timers.py`, `ScheduledTimer`, the queue subscriber `core/queue_worker.py`) and generic presence (`core/presence.py`). A game app plugs in through `apps/core/games.py`: `GameHooks` registered per `Lobby.game_type` from `AppConfig.ready` (`apps/onuw/hooks.py`: settings validation, the newest game's socket group, who is connected to it, when its players were noticed gone, whether it is finished, which game a member plays in: `member_game`) plus `timers.register_job_module` and `presence.register_scope`. ONUW keeps the game: `Game`, `PlayerRole`, `SocketPresence` (GAME sockets only), its services and its timer jobs.

**Durable timers (`apps/core/timers.py`).** A timer is a named job with JSON params stored in `ScheduledTimer` (unique `key`, random `token`, `due_at`, `job`, `params`): `timers.schedule(key, delay, job, params)` upserts the row with a fresh token and arms the backend; `cancel(key)` deletes the row; `cancel_all_for_game(game_id)` deletes by `"<game id>:"` prefix; `is_scheduled(key)` checks the row (memory: also that a thread is armed in this process; queue: also not overdue by more than 120 s). Handlers register with `@timers.job("name")`: `night_window` (deadline AND the deferred minimum-length close, `deferred` param), `discussion_deadline`, `voting_deadline`, `grace_expired`, `host_handover`, `presence_check`. Callers still schedule after commit (`services._schedule_after_commit(key, delay, job, params)`). `timers.fire(key, token)` is the one runner for every backend: it locks the row, runs only if it still exists with that token and is due (2 s of clock skew tolerated; earlier = "early", the subscriber re-sends with the remaining delay), deletes the row in the SAME transaction and runs the job inside it, so a stale token, a cancelled key or a duplicate delivery does nothing and two instances cannot both run it; the handlers' phase / window checks are a second guard. A job that FAILS must raise: every real job logs and re-raises (`make_idempotent_callback(..., reraise=True)`, `_grace_expired`, `_handover_due`, the presence check), so `fire` rolls back and the row survives for a retry (memory backend: `_thread_fire` retries after `RETRY_DELAY_SECONDS` = 5, at most `MAX_ATTEMPTS` = 5 times; queue backend: the worker raises the SDK's `RetryAfter(15 s)` until `delivery_count` reaches 5, then drops the message and leaves the row for the sweep). `run_job_quietly` is for tests' fake schedulers only. **Lost firings:** the row records `published_at` (set only after the queue send returned / the thread was armed) and `scheduled_at`; under the queue backend a row unpublished for more than 5 s is NOT `is_scheduled`, so the lazy `ensure_timers` re-publishes it, and `timers.sweep(prefixes)` re-sends (SAME token; a duplicate is harmless) unpublished rows and published rows more than 5 s past due (at most every 30 s per row); under the memory backend it re-arms threads this process lacks. `GET /me/` sweeps its own game (`services.timer_prefixes`); `GET|POST /api/onuw/internal/sweep-timers/` sweeps everything for a platform cron and answers 403 unless `Authorization: Bearer <CRON_SECRET>` (setting `ONUW_CRON_SECRET`, env `CRON_SECRET`) matches (no secret configured = always 403). **Clocks:** `due_at`, `scheduled_at`, `published_at`, `last_seen` and every freshness / due comparison use the DATABASE clock (`Now()`), never an instance clock. Backends: `memory` = `threading.Timer(key, token)`; `vercel_queue` = delayed message `{key, token}` (`vercel.queue` imported lazily, optional extra `vercel`) handled by `apps/onuw/queue_worker.py` (registered as `[[tool.vercel.subscribers]]`). The debug `fire-timer` claims the row with `fire(..., force=True)`; `current` ignores `:grace:` keys, and the `lobby:` / `presence:` keys never match a game's prefix.

**Timers survive a restart (memory backend).** The stored `Game.phase_deadline` / `night_window_opened_at` are the truth. `services.recover_timers()` (never under the queue backend: `run_startup_recovery` returns at once) runs once at server start (`run_startup_recovery()`, called from `config/asgi.py`; it runs in a short-lived joined thread so it works even when the server imports the app inside a running event loop, and closes that thread's DB connections; switched off by `ONUW_RECOVER_TIMERS_ON_START = False` in the test settings, never runs in migrations or management commands, tolerates an unmigrated DB). It does NOT reset presence (below), opens a night that crashed before its first window, calls `ensure_timers(game)` for every game in night / discussion / voting, then `timers.rearm_from_table()` re-arms every other stored timer (presence checks) that has no thread here. `ensure_timers` re-creates what is missing (`timers.is_scheduled(key)` is the cheap check): the phase or window timer (a deadline that is overdue or less than `RECOVERY_RECONNECT_ALLOWANCE_SECONDS` = 15 s away is first moved to now + 15 s and persisted, so phones can reconnect before the vote is revealed or the night closes; the same happens in the lazy path only when the timer is genuinely missing; the extension depends only on the clock, so the fixed Doppelganger window's length still says nothing about her), the night's deferred "everyone acted, minimum length not passed" close (due at the minimum, not the deadline), and dropped players' grace timers. The Doppelganger window only ever gets its fixed deadline. `GameMeView` calls `ensure_timers` on every fetch, so a game also repairs lazily. Safe in several workers: every callback locks the Game row and checks the phase, and the night callbacks check the window number (`_auto_advance_wave`), so a stale window-1 timer cannot close window 2. A minimum-length (deferred) close re-checks readiness under the lock when it fires (a player treated as gone may have come back); if the window is no longer ready it puts the normal deadline timer back, and a reached deadline always closes. A phase with no deadline (`discussion_seconds`/`voting_seconds`/`night_wave_seconds` = 0) has no timer by design: only the host (or, for the vote, the last voter) moves it.

**Play again.** (The generic part, `core/lobbies.py`: host check, reopen, ready flags, events, asks the game hooks whether the newest game is finished.) `Game.lobby` is a ForeignKey (`related_name="games"`); a lobby's current game is its newest (`services.latest_game`). `POST /api/lobbies/<code>/play-again/` (also `/api/onuw/lobbies/<code>/play-again/`, same view, name `lobby-play-again`) is host-only (403), needs the newest game in `results` (409; a repeat while already `waiting` is a harmless 200), sets the lobby `waiting`, sets every member ready, keeps members and settings, and answers with the lobby detail body. `POST .../start/` locks the Lobby row from the status check to creating the Game, so a double tap deals one game, and opens the first night window in that same transaction (side effects after commit), so there is never a committed night without a window; a night still at window 0 more than `NIGHT_START_STUCK_SECONDS` (15) after creation is opened by the lazy `ensure_timers` (`GET /me/`); a younger one is left to its starter. `GET /me/` has `lobby_code` in every phase. After commit: `play.again` on `game_<old id>` (client sees `{"type": "play_again", "lobby_code"}`) and `lobby.update` on `lobby_<code>`. The old game and its results stay readable; `CurrentGameView` skips finished games so nobody is sent back into them. Leaving between games works as before (host leaving deletes the lobby; a non-host leaving may leave the deck mismatched, so the host PATCHes settings before dealing).

**Dropped phones.** Presence is one row per open socket (`SocketPresence` for a game socket, `core.LobbySocket` for a lobby socket: `user`, the game or lobby, unique `channel_name`, `connected_at`, `last_seen`), never a counter and never reset at start-up. `GameConsumer`/`LobbyConsumer` insert the row on connect, delete it on disconnect and refresh `last_seen` every `ONUW_PRESENCE_HEARTBEAT_SECONDS` (15; an asyncio task per consumer; each beat is a short non-thread-sensitive DB call that releases its connection). A user is *connected* in a scope while a row has `last_seen` newer than `ONUW_PRESENCE_STALE_SECONDS` (40) (`presence.fresh_rows`, `connected_user_ids`). **Silent deaths** (instance killed, no `disconnect`): when a row is created or refreshed a durable `presence_check` timer (key `presence:<game|lobby>:<id>:<user>`, one pending per scope+user) is ensured, due at `last_seen + stale`; a heartbeat writes no timer, the check re-arms itself when it fires early (about one timer write per staleness period), and when it fires on a user with no fresh row it deletes the stale rows (the healthy path, a fresh row, takes NO Game/Lobby lock: it only re-arms; the stale path re-checks under the usual locks) and runs EXACTLY the clean last-socket path (`services._game_went_offline` / `host._lobby_went_offline`). The "gone since when" stamps stay as `PlayerRole.disconnected_at` and `LobbyMember.disconnected_at` (set when noticed, cleared on coming back; a silent death starts its grace clock when noticed, not at the last beat). Transitions are under row locks (Game then PlayerRole; Lobby then LobbyMember) in `register_connection` / `unregister_connection` / `refresh_connection` / `check_game_presence` and `host.register_lobby_connection` / ... . 0 to 1 and 1 to 0 broadcast `player.presence` (client: `{"type": "player_presence", "player_id", "connected"}`); `PlayerListView` has `connected` per player (fresh rows). Setting `disconnect_grace_seconds` (default 25, 0 to 60, 0 = off). When the last socket goes during night or voting a grace timer (`<game>:grace:<user>`) starts; a player disconnected at least the grace period is "gone": the night window may close once every *other* actor has acted (through `_close_or_defer`, so the minimum window length and the fixed Doppelganger window still apply, and the missing player is a timeout), and the vote is revealed once everyone else has voted (the missing player is a non-voter). Discussion never waits. Reconnecting cancels the timer and re-checks readiness. Two deliberate choices: (1) while a player is *inside* their grace period the night window waits for them whether or not they have an action, otherwise the close time would tell the table whether the dropped player was an actor; (2) if every phone is gone nothing closes early (only the deadline or the host). A player never seen disconnected has no `disconnected_at` and is never treated as gone. Host endpoints (`advance-wave`, `end-discussion`, `reveal-votes`) work with players dropped; a gone owner is replaced by host handover (below).

**Host handover.** `Lobby.host` is the owner and never changes; `Lobby.acting_host` (nullable) holds the role while the owner is away. The *effective host* is `acting_host` if set, else `host`; EVERY host-only check calls `Lobby.is_host(user_id)` (start, lobby settings PATCH, advance-wave, end-discussion, reveal-votes, play-again, `is_host` in `/me/`, the debug oracle). Logic lives in `apps/core/host.py`. Setting `host_handover_seconds` (default 60, 0 to 600, 0 = off, read from the lobby settings; the same limits are validated by `apps/onuw/engine/validation.py`). When the effective host has had no open socket (a fresh lobby socket row OR a fresh newest-game socket row; lobby presence is never broadcast) for that long, the first lobby member in join order who is connected becomes the acting host; if nobody is connected nothing happens until someone connects; an acting host who drops for the same period hands on again, never to the absent owner. The moment the owner has a socket the acting host is cleared (no delay). An acting host who *leaves the lobby* passes the role to the next connected member, or to nobody (the role is then back with the owner, reason `returned`); **the owner leaving** is refused while a game runs (409); otherwise, if anyone else is in the lobby, the table is NOT deleted: ownership moves for good to the next member in join order (a connected one preferred), `acting_host` is cleared, the leaver's membership and sockets go, and `host.changed` goes to the lobby and the newest game's group with reason `transferred` (`host_id` == `original_host_id` == the new owner; finished games stay readable by those who remain). Only the last member leaving deletes the lobby. Event `host.changed` to the lobby group and the newest game's group, only on a real change: clients receive `{"type": "host_changed", "host_id", "host_name", "original_host_id", "reason": "handover" | "returned"}`. Lobby detail: `host` is the effective host (`{id, username, display_name}`), plus `original_host_id` and `is_acting_host`; `/me/` has `host_id` (effective) and `is_host`. Timer key `lobby:<lobby id>:host` (job `host_handover`; cannot match a game's `<uuid>:` prefix, so the debug fire-timer `current` and `cancel_all_for_game` never see it). Nothing is reset at a restart: the owner's rows go stale, the presence check notices (stamping `LobbyMember.disconnected_at`) and the owner's minute starts then; nobody is handed the role until someone is connected. Lock order is now Game -> PlayerRole -> Lobby -> LobbyMember; host code takes Lobby then LobbyMember and never a Game/PlayerRole lock while holding them, and runs only after the game presence transaction commits (a silent-death check schedules `host.game_presence_changed` with `_after_commit`). The owner leaving locks the Lobby row first, so a concurrent presence check waits, then finds the lobby gone (or the new owner) and does nothing.

**Missed night results.** `GET /me/` has `night_results`: the caller's own results for closed windows, `[{"wave", "action_type", "revealed_info"}]`, built from the night log by `services.client_action_result` (the same transform the `action.result` socket event uses) so the two cannot drift. One entry per result in window order (a Doppelganger with a follow-up gets two in window 1), skips omitted, nothing for a window still open (including her early look), nothing of anyone else's.

**Tokens, seats, deal snapshot.** Each `LobbyMember` has a `token` (`core/tokens.py`: ten ids, a permutation seeded by the lobby code, the first free one is taken at join / create by `lobbies.add_member` under the Lobby row lock, logged at INFO; capacity is checked there too, so the join is atomic; every join refusal has a `code`: `lobby_not_found` 404, `already_in_lobby`, `lobby_closed`, `lobby_full` 400; `max_players` is capped at create by the token count, `core.tokens.MAX_TABLE_SIZE` = 10, the one home of the limit; the game checks its own 3 to 10 when it deals). The token is freed when the member's row is deleted and stays across play again. `GameStartView._deal` validates everything first (a refusal returns inside `atomic()`, which would COMMIT earlier writes, so `post` also calls `transaction.set_rollback(True)` on one), then gives a blank token to any member who has none (`lobbies.ensure_tokens`: rows made by code from before tokens), then `_snapshot_player_roles` copies token and seat (join order) into `PlayerRole.token/seat`, and the dealt center goes to `Game.dealt_center_cards` (`Game.center_cards` is overwritten by the night). `PlayerRole` orders by `(seat, user_id)`; every players list uses `serializers.player_identity`. `PlayerRole.phase_ready` and `night_results_seen` exist for later slices (`api-contract-v2.md`).

**Where am I.** `GET /api/me/table/` (`core/lobbies.current_table`, view `MyTableView`) starts from MEMBERSHIP, not from games: the caller's newest-joined `LobbyMember` whose lobby had activity within `CORE_TABLE_RESUME_HOURS` (default 12; `Lobby.updated_at`, which create, join, leave, settings, deal, finish, play again and host changes all bump, via `save()` or `lobbies.touch`; an `in_game` table nobody finished expires too). It answers `{"table": {"lobby_code", "game_type", "status", "is_host", "token", "game": {"game_id", "phase"} | null}}` or `{"table": null}`; `game` comes from `GameHooks.member_game(lobby, user_id)` (the lobby's newest game if the caller plays in it, so after "play again" the lobby is `waiting` while `game` is still the old results game). The client routes: `game.phase != "results"` -> the game, `status == "waiting"` -> the lobby, `finished` -> the results. `CurrentGameView` is unchanged.

**Deploy-safe changes (the previous code serves while `migrate` runs on every deploy).** Checked by tests and `just check`, not by habit:
- **Migrations are frozen once pushed.** Every push migrates the live database; to change the schema again, add a NEW migration, never edit a pushed one. `just check` runs `makemigrations --check --dry-run` (a model change without its migration fails the gate and CI).
- **No application code in a migration** (no `from apps...`): copy what it needs, frozen. `tests/test_migration_rules.py` scans every migration file.
- **`SET LOCAL lock_timeout = '5s'` is the first operation** of every migration from 0010 on (same test), so an ALTER that cannot get its lock fails the build instead of blocking the live site behind it.
- **Every new NOT NULL column has a `db_default`** (and a Python `default`), because the old code's INSERTs omit it. A backfill touches only what it must (finished tables stay blank) and new code treats a blank value as "not backfilled yet" (a blank token is filled at the deal).
- **The migration test gains a case per migration.** `tests/test_migrations.py` (marker `migration`) applies the REAL migrations (the rest of the suite uses `--nomigrations`, where these tests skip), seeds old-shape rows through the historical models, migrates forward, asserts, runs the old code's INSERTs (`tests/old_code.py`, never add columns to them), then back and forward again. `just test` runs it as a second pass (`just test-migrations`, about 5 s); CI runs `just test`.
- **A new socket event type reaches instances that have no handler:** consumers extend `core.consumers.TolerantJsonWebsocketConsumer`, which logs an unknown type at WARNING and drops it (and raises when `ONUW_STRICT_SOCKET_EVENTS` is true: test, development and harness settings, so a misspelled type in new code still fails the suite).

**Night results ack.** `GET /me/` has `night_results_seen` (the caller's own count, `PlayerRole.night_results_seen`); `POST /api/onuw/games/<id>/night-results/seen/` with `{"seen": n}` (a plain JSON integer 0-10, else 400 `bad_request`; 404 unknown game, 403 not a player) answers `{"night_results_seen": <stored>}`. `services.acknowledge_night_results` clamps `n` to the number of `night_results` the caller can see NOW (the Doppelganger's look is sent by socket while window 1 is open but listed only once it closes, so an early ack cannot cover it) and raises the stored count with ONE `UPDATE ... SET n = GREATEST(n, :value)` (no Game lock, never lowers). The client shows `night_results[night_results_seen:]` and acks after each window's dawn screen, sleepers too. `tests/onuw/test_v2_payloads_no_leak.py` sweeps the v2 payloads for foreign role names.

**Lock-in voting.** `POST .../vote/` takes `{"target_player_id": <JSON integer>, "lock": <bool, default true>}` (anything else is 400 `bad_request`: no coercion). A vote is *picked* (`PlayerRole.vote_target`, `has_acted` false, changeable, NO socket event at all) and then *locked* (`has_acted`, final; any pick or lock after it is 409 `vote_locked`). Answers: locked `{"status": "submitted"}` (today's shape), picked `{"status": "picked", "target_player_id": N}` (the stored target). Errors carry `code` (`wrong_phase`, `invalid_target`, `bad_request`, `vote_locked`; `detail` of a 400 from the service stays a LIST of messages as it always was). `services.submit_vote(game, voter, target, *, lock=True)` is ONE transaction: Game lock, phase re-checked, voter's PlayerRole lock, validate, store; a lock sends the legacy `vote.submitted` (who) and the group `progress {stage: "vote", done, needed}` (counts of the players not gone past grace) after commit, then reveals if `_votes_ready` (so two last locks reveal once and a vote cannot land after the reveal). **At any reveal every stored pick counts, locked or not** (`reveal_votes` reads `vote_target` for everyone; a dropped player's pick and an unlocked Hunter's pick count): it is a rule of the spec (`voting-and-resolution.md`), not an accident. `progress` is also sent when the vote opens (`done` 0) and when presence changes `needed` (`_evaluate_presence`). `/me/` has `my_vote` (the caller's own `{target_player_id, locked}` while voting, else null), `ready` (own flag, at the look stage and in the talk) and `progress` (`services.stage_progress`). The debug oracle has `vote_locked` per player next to `votes`, and `ready` per player.

**Ready to vote (the talk).** `POST .../ready/ {"ready": <bool>}` (`ReadyView`, `services.set_ready`; strict bool else 400 `bad_request`; 403 not a player; 400 `wrong_phase` outside the talk and the look stage) toggles `PlayerRole.phase_ready` (reset by `transition_to_discussion`) and answers `{"status": "ok", "ready": <stored>}`. One transaction (Game lock, PlayerRole lock, phase re-checked): every tap recounts `needed` (players not gone past grace) and sends `progress {stage: "talk", done, needed}`; when `done == needed >= 1` it calls `end_discussion`, the host button's own function, so a tap racing the host or the talk's deadline ends the talk once (the loser gets the ordinary wrong-phase 400). The talk never WAITS: readiness can only end it early, and there are NO grace timers in the talk, so a talker who went away is only left out of `needed` on the next tap; a phone that had been gone past grace coming back sends the new count (`register_connection`) but never ends the talk.

**Look stage (`card_look_seconds`).** A game setting, 0 to 120, default 0 = off = the deal opens the first window as before. When > 0 the deal (`services.begin_night`, called last by `GameStartView._deal`) does NOT open a window: the game stays in night, window 0, with `phase_deadline` = now + the setting (`_in_look_stage`: night, window 0, a deadline set) and a `card_look` timer (key `<game id>:look`, scheduled ONLY when the setting is > 0, so an old instance never gets a job it cannot run), and sends `progress {stage: "look", done: 0, needed}`. Every phone taps `POST .../ready/ {"ready": true}` (`false` is 400 `bad_request`: looking is one way); `ready` at any other window is 400 `wrong_phase`. The night opens (`start_night_phase`, idempotent under the Game lock, which also cancels `<id>:look`) when every player not gone past grace has looked, when the backstop fires, or when the host taps advance-wave (`advance_wave` at window 0 opens the first window; it used to raise). A tap that loses the race to the backstop gets the ordinary `wrong_phase` 400. **One readiness rule:** `_stage_is_ready` (look and talk: `needed >= 1` and `done == needed`) and `_advance_stage_if_ready` are used by `set_ready` (a tap), `_evaluate_presence` (a grace period ended, a phone came back: it re-checks, else re-announces the count) and `ensure_timers` (the look timer was lost: if everyone present has already looked it opens the night, else it rebuilds `:look` with the reconnect allowance). `_night_start_is_stuck` only applies when there is no deadline (a look stage is waiting for taps, not stuck), and `recover_timers` does not open a window-0 night that has a look deadline. `advance-wave` accepts `{"from_window": n}` (0, 1 or 2; absent = no check) and answers 409 `wrong_window` when the game is in another window, so a stale host tap cannot close the next window. The debug fire-timer accepts `key: "look"`; `current` already finds it. `/me/` `progress` is `{"stage": "look", ...}`, `ready` is the caller's own flag, `deadline` is the look deadline, `action_prompt` is null for everyone.

**Night protocol 2 (`settings["night_protocol"] == 2`): every phone sends one `choose`.** Games without it (the default, and every game the old screens deal) keep the per-role night above, untouched; `services.is_choose_night(game)` is the one switch, and `night_protocol` must be 1 or 2 (validated at the lobby and at the deal). Under 2: `POST .../action/ {"action_type": "choose", "picks": [...]}` from EVERY player, 0 to 2 distinct ordered picks (`{"player_id": n}`, `{"center_index": n}`, `{"self": true}`; a pick of your own id is `self`). The PURE `engine/choose.py` parses the picks (`parse_picks`: malformed = not a list, over 2, an item that is not exactly one known key with a plain JSON integer / `true`, a stranger, an off-board centre index, a duplicate) and reads them per role (`interpret_choice`: Seer two centre picks or the first other player; Robber the first other player; Troublemaker two other players; Drunk the first centre card; a LONE Werewolf the first centre card; the Doppelganger's look the first other player; everything else nothing; the first valid action in tap order, "You" never a target). A pick that reads as nothing is NOT an error: it is stored as "chose, nothing valid" and the window close applies the role's timeout default (a Drunk is swapped by the server with `made_by_server`, team views and the Insomniac still happen, a lone Werewolf still learns it is alone, Seer / Robber / Troublemaker / the look skip). A Doppelganger's follow-up is read as the copied role. **Identical answers:** every choose is `200 {"status": "submitted"}`; the only refusals are `wrong_phase` (400: not in an open window, including the look stage), `already_chosen` (409: window 1 takes two chooses from every phone, window 2 one) and `bad_request` (400, malformed; any other `action_type` too), none depending on role (403 for a stranger). The count is `night_action_data["chose_<window>"]` (no new column; kept by `persist_wave_results`). **Events:** a window opens with ONE group event `night.window {window, deadline}` (client `night_window`) and closes with the group `wave.complete`; there is NO per-player event in the night at all (no `action.prompt`, `wave.waiting`, `action.result`; the Doppelganger's look is not sent either). **`GET /me/`:** `action_prompt` is present for every player in an open window with one shape (`engine.choose.build_choose_prompt`: `window`, `kind` = `none|seer|robber|troublemaker|drunk|lone_werewolf|doppelganger_look`, `role_acting_as` (your own), `action_types: ["choose"]`, `max_picks`, `max_chooses`, `chosen`, and the same board for everybody; no teammates; a lone Werewolf's `kind` states its real option), and `night_results` lists the Doppelganger's look as soon as it resolves (her own, while window 1 is open). `revealed_info` role names are canonical (`"Werewolf"`) instead of lower-cased, `copied_role` as always. **Closing:** window 1 stays fixed-length; window 2 closes when EVERY present phone (not gone past grace; a phone still inside grace holds it) has chosen once, never before `night_min_window_seconds` (via `_close_or_defer`), else at the deadline, so the close time cannot say who had a choice. `ONUW_ALLOW_UNTIMED_NIGHT` (base False; True in the test, development and harness settings) gates protocol-2 games with `night_wave_seconds` / `night_doppelganger_window_seconds` of 0 or `night_min_window_seconds` under 5: refused at the lobby and at the deal where it is False. With the fixed Doppelganger length off (dev only) window 1 waits for every phone's two chooses.

**Automatic deck and create defaults.** Lobby settings may say `deck: "auto"` (or `"custom"`) and `deck_chip` (`simple|classic|chaos`, default simple; validated at PATCH and deal). With `auto` the host's card list is ignored and the DEAL (`GameStartView._deal`, under the Lobby row lock) builds the deck for the players at the table now from `engine/decks.py` `DECK_TABLE` (3 to 10 players x 3 chips, each exactly players + 3 legal cards) into the GAME's settings only: the lobby keeps saying `auto`, so play again with one more player deals the next row. The doc table in `docs/specs/onuw/recommended-setups.md` ("Automatic Decks") is compared with `DECK_TABLE` by `tests/onuw/test_auto_deck.py`, which also checks all 24 rows are legal decks. `POST /api/lobbies/` takes an optional `defaults: "v2"` (any other value: 400 `bad_request`) that `GameHooks.default_settings` answers with `hooks.V2_DEFAULTS` (Normal pace: discussion 300, voting 90, night wave 30; `card_look_seconds` 30; `night_doppelganger_window_seconds` 15; `night_protocol` 2; `deck` auto, chip simple); settings given in the body win; without `defaults` nothing is written.

**Night timeline (results).** `GET .../results/` (results phase only, members only, as before) has `night_timeline`: `{seats, cards, dealt, steps, final, center_moved}` built by the PURE `engine/timeline.py` (`build_night_timeline`) FORWARDS from the dealt cards (`PlayerRole.original_role` by seat, `Game.dealt_center_cards`) and `Game.night_actions_log` (`ActionLogEntry.to_dict` is the one log format). Cards have stable ids (`k0..k<n-1>` by seat, then the three centre cards) and a server-set `werewolf` flag (a Werewolf card, or a Doppelganger card whose holder COPIED Werewolf: it is a werewolf card for whoever ends the night holding it, `docs/specs/onuw/doppelganger.md` Team Resolution Rule); each step is one log entry in WAKE order (the engine resolves team views in SEAT order, so inside order group 2 the timeline re-sorts to Werewolves, Minion, Masons with a stable sort; team views move no cards; `see_team` rows of one role in one group merge into ONE step with all its actors, dealt ones first, a Doppelganger who copied the role among them and named in `doppelganger_actors`; a Doppelganger-Minion acts in window 1 and keeps her own step) with `actors`, `doppelganger_actors`, `action` (`copy`, `see_team`, `peek_player`, `peek_center` (a lone Werewolf's look too), `swap_with_player`, `swap_others`, `swap_with_center`, `look_own`, `skip`), `looked_at` (card ids as the table was at that step), `moves`, `team`, `copied_role`, `made_by_server` and `positions_after`. A game dealt before `dealt_center_cards` recovers the centre with `recover_dealt_center` (undo the logged swaps from the final table and require the players' cards to equal their dealt roles). The undo checks ONLY that the players' cards come back to their dealt roles (the centre it returns is what the log implies). `services.night_timeline_for` is a presentation boundary: ANY failure answers `night_timeline: null` so the rest of the results still show; a refusal for a game from before the centre was stored is logged once at WARNING, anything else at ERROR. The proof is in the tests, not a runtime self-check: the replay's final table equals the engine's for all 29 reference games and 1500 seeded random nights, with the actions collected the way the server collects them (`tests/onuw/night_rules_reference.engine_night`: seat order, a Doppelganger's follow-up last) and seats the reverse of player-id order (`tests/onuw/test_night_timeline.py`).

**Home extras and settings.** `GET /api/stats/online/` (`OnlineStatsView`, no login, `authentication_classes = []`, its own throttle scope `online_stats` = 60/min so the home screen cannot eat guest sign-up's `anon` budget; `Cache-Control: public, max-age=15, s-maxage=15`, which PERMITS 15 s reuse by browsers and shared caches and guarantees nothing more: whether a CDN honours it is the platform's choice. **DRF throttles count in the default cache, a per-process LocMem cache, so on Vercel every instance has its own budget (the limit is per instance, not per client), and `AnonRateThrottle` keys on the client address taken from `X-Forwarded-For`, which a caller can spoof; treat the throttles as a courtesy, not a defence**) answers `{"players", "tables"}`: distinct users and lobbies with a FRESH socket row on the database clock (`core/online.py`: core's `LobbySocket` rows plus the sources a game app registers with `online.register_online_source`; ONUW registers `presence.online_sockets` for `SocketPresence` in `AppConfig.ready`). It counts sockets, so someone on the home screen is not counted: label it "players at tables". `GET /api/onuw/me/recent-games/?limit=` (default 5, 1..10) lists the CALLER's games in `results`, newest first: `{game_id, ended_at (Game.updated_at), player_count, winning_teams, you_won, token, seat}`; no lobby code, nothing about others. `PATCH /api/lobbies/<code>/` MERGES the given `settings` keys over the stored ones (shallow: a key given again is replaced whole), under the Lobby row lock, host only, 409 `lobby_in_game` while a game runs (a finished table may change the deck for the next game), 400 if `settings` is not an object, and the game's validator checks the MERGED result (nothing is stored if it refuses; the deck-against-player-count check runs only when `roles` is in the PATCH, via the hook's `changed` keys, so a pace-only PATCH is not refused because a player joined; the deal checks again); there is no way to delete a key, send its default. `pace` (`quick`, `normal`, `long`, `custom`) is validated if present and never read by the server. The ready toggle is refused while a game runs (409 `lobby_in_game`) and takes the Lobby lock like the deal.

**Action types:** `peek_player`, `peek_center`, `swap_with_player`, `swap_with_center`, `swap_others`, `see_team`, `none`, `skip` (explicit "do nothing": Seer, Robber, Troublemaker only, including a Doppelganger follow-up as one of them; advertised in the prompt's `action_types`; never for the Drunk, the Doppelganger's first look, or view-only roles)

**v1 roles (12):** Werewolf, Villager, Seer, Robber, Troublemaker, Drunk, Insomniac, Minion, Tanner, Hunter, Mason, Doppelganger

**Win conditions:**
- Village wins if a Werewolf is eliminated
- Werewolves win if no Werewolf is eliminated
- Tanner wins if Tanner is eliminated (overrides village win)
- Hunter kills the player they voted for if Hunter dies
- No werewolves in play → village must NOT vote to kill anyone to win

**Critical edge cases:**
- Player disconnects mid-action → action skipped after timer (or after the grace period if everyone else is done)
- Timer expires with no submission → action skipped
- Doppelganger copies a role with a night action → acts again (Seer/Robber/Troublemaker/Drunk/Minion immediately in window 1; Werewolf/Mason/Insomniac in window 2)
- All votes tied → no one dies
- Robber swaps then Troublemaker swaps the same player → order matters (resolution order within window 2 settles this)

## Silent Failure Modes

- **WebSocket connections require JWT auth.** The ASGI middleware validates tokens. Tests need `WebsocketCommunicator` with an authenticated user scope — unauthenticated connections are rejected silently.
- **Throttle rates must be configured in test settings.** Guest auth endpoints use DRF throttling. If `DEFAULT_THROTTLE_RATES` is missing from test settings, guest creation tests fail with 429s that look like server errors.
- **Error messages must not leak role information.** Validation errors for night actions must use generic messages (target values must be plain JSON integers: anything else is a 400, never coerced) ("invalid action") not role-specific ones ("Seer cannot do that") — the role name itself is hidden information.
- **Night action TOCTOU race.** Concurrent action submissions for the same player must be guarded with `select_for_update()`. Without it, two simultaneous requests can both pass validation and both write.

## Adding a New Role

Requires updates in multiple files — the type system won't catch a missed one:

1. `engine/roles.py` — role definition and metadata
2. `engine/behaviors.py` — night action behavior
3. `engine/night.py` — wave assignment
4. `engine/win_conditions.py` — if the role affects win logic
5. `serializers.py` — if the role has special display rules
6. Tests for each of the above

## Adding a New Django App

The `apps.` prefix in the app name is required and easy to forget:

```python
# apps/myapp/apps.py
class MyappConfig(AppConfig):
    name = "apps.myapp"  # NOT just "myapp"
```

Then add `"apps.myapp"` to `INSTALLED_APPS` in `config/settings/base.py` and create test directories under `tests/unit/myapp/` and `tests/integration/myapp/`.

## Contract samples

`tests/contract/` records what the server sends, for the app's tests: `scenarios.py` plays three tables (a classic six-player game with the default timers, "where am I" in every state, the night results ack, recent games and online stats; an untimed eight-player game with a Doppelganger, every remaining prompt kind and the night timeline, then more games there by play again (she copies a Werewolf, a Mason, an Insomniac, the Minion; a dealt Tanner dies); a full ten-player table for the join refusals) through the real API (`recorder.Table`: DRF test client against the URL conf; a `RecordingLayer` channel layer whose group messages are turned into client frames by the consumers' own handlers; on-commit effects run per request; real timer rows with no thread, `is_scheduled` = the row exists, fired by claiming the row; clock frozen at a past date, user ids from 1, fixed lobby codes and forced-deal seed; game ids, guest usernames and tokens replaced by stable stand-ins). Each socket sample's index entry has `group` (`player` or `broadcast`) and `recipients`; `test_contract_privacy.py` fails if a night prompt, result or `wave_waiting` is broadcast, or a game broadcast before the results names a role. `test_contract_samples.py` writes them to `contract_samples/` at the repo root with `UPDATE_CONTRACT_SAMPLES=1` (`just samples`) and otherwise fails, with a diff, if the committed files differ. A new endpoint, event or situation is a `table.record(...)` / `table.record_event(...)` line in `scenarios.py`, then `just samples`. A payload change shows up as a diff of the samples (review it), and may fail the app's tests where a fixture relied on the old shape.

**Night protocol 2 samples.** `scenarios.protocol_two_tables` (after the three tables above, so their samples never move) plays four more tables: a plain five-player table made with `defaults: "v2"` (the look stage with `ready` / `progress`, window 2 where every phone chooses once, the lone Werewolf's prompt, every `choose` answer and refusal, ready to vote, the lock-in vote with pick / re-pick / lock / 409, the oracle), an eight-player Doppelganger table (window 1 with two chooses per phone, her look listed at once, then window 2 and every prompt kind), and the automatic deck at 5 (classic) and 9 (chaos) players. **A game without `night_protocol: 2` is answered exactly as before** (no `my_vote` / `ready` / `progress` in `/me/`, no `code` and the old wording in vote errors, no `ready` / `vote_locked` in the oracle): the original samples must not change, and a diff in one is a behaviour change to fix, not to regenerate. `Table.record_sequence` stores per seat the TYPES of the game events heard in a window (`ws_sequence/*`); the privacy test requires them equal for every seat and free of player-only night events, and every `night_window` / `progress` / `wave_complete` sample to be a broadcast.

## Debug / Harness (DEBUG-only)

For the integration harness there are `DEBUG`-gated affordances (all 403 in production, each with a rejection test): a forced-assignment / seed override on game start (`GameStartView`), a `debug-state` full-state oracle (its `connected` is real socket presence; `pending_timers` lists the armed timers), and a `debug-fire-timer` hook (`wave:1` / `wave:2` close that night window now; `current` ignores grace timers) — see `apps/onuw/debug.py` + `debug_views.py`. Game timers are per-game settings, so the harness and `tools/game_driver.py` set `night_min_window_seconds`, `night_doppelganger_window_seconds` (and the other timers) to 0 for speed. Boot the harness backend with `just harness-serve` (`config.settings.harness`: `DEBUG=True`, throwaway DB `midnight_village_harness`, `127.0.0.1:8001`). `tools/game_driver.py` is a CLI that drives a whole ONUW game through these. Full docs: `docs/dev/debug-harness/`.
