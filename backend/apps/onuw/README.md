# apps.onuw: how the game works on the server

The as-built behaviour of the ONUW app, endpoint by endpoint. The rules of the game are in
`docs/specs/onuw/`; the v2 API decisions are in `docs/specs/onuw/api-contract-v2.md`; this is
what the code does today. Shared infrastructure (timers, presence, host, lobbies) is in
`apps/core/README.md`; test conventions in `tests/README.md`. Keep this file true when you
change the code it describes.

## The night: two windows

**Night phase runs in two windows** (`Game.current_wave` holds the window number: 1 or 2, 0 outside night). `RoleDefinition.wave` is the *order group* (position in the wake order), not a phase of the game; action-log entries are tagged with it so the log stays in wake order.

1. **Window 1 — Doppelganger alone.** Runs whenever the Doppelganger card is in the deck (dealt or in the center), even if nobody can act. It lasts **exactly** `night_doppelganger_window_seconds` (default 10) whatever happens in it (nobody to act, look submitted or not, follow-up or not): one timer is set when it opens, nothing reschedules it, and `phase_deadline` is the real close time. `0` turns the fixed length off: window 1 then closes like window 2. The look resolves and is sent on submit; a follow-up as Seer/Robber/Troublemaker/Drunk/Minion is prompted on submit but resolves when the window closes; anything unsubmitted is skipped.

2. **Window 2 — everyone else at once.** Always runs, even if nobody has a choice. Every actor is prompted together: dealt Werewolves, Minion, Masons, Seer, Robber, Troublemaker, Drunk, Insomniac, and a Doppelganger who copied Werewolf/Mason/Insomniac. Nothing is sent to anyone until the window closes; then the engine resolves, each step seeing the table after the previous one: team views (group 2), Seer -> Robber -> Troublemaker -> Drunk (group 3, Doppelganger before the real role), Insomniac (group 4). Engine entry points: `get_required_actions_for_window`, `resolve_window` (`resolve_night` still takes actions keyed by order group 1-4).

- **Timing (window 2)** (every length here is the table's own setting; nothing else may add a wait): a window closes when its last actor submits, but never sooner than `night_min_window_seconds` (default 8) after it opened (the close is scheduled for that moment); `night_wave_seconds` (default 30) is the maximum. Host "advance" closes any window immediately. Timer settings (`night_wave_seconds`, `night_min_window_seconds`, `night_doppelganger_window_seconds`, `discussion_seconds`, `voting_seconds`; and `disconnect_grace_seconds`, 0-60; `host_handover_seconds`, 0-600) are validated in `validate_onuw_settings` (integers 0-3600; min window <= `night_wave_seconds` when that is > 0); `get_timer_seconds` falls back to the default on a bad stored value.

- **Side effects after commit:** every WebSocket send and `timers.schedule` / `cancel` in the night flow goes through `transaction.on_commit` (`_send_after_commit`, `_schedule_after_commit`, `_cancel_after_commit`), so a rollback leaves nothing sent or rescheduled. Payloads are built inside the transaction. Job exceptions are logged by `make_idempotent_callback`. How to test these: `tests/README.md`.

- **Dealt-card rule:** who wakes as a Werewolf or Mason, who acts in every step, and who a Minion sees is decided by the card DEALT (`state.original_roles`) plus a Doppelganger who copied that role, never the card held mid-night. A stolen Werewolf card does not make the thief a Werewolf; the player it was taken from still wakes (and can be the "lone" Werewolf). Winning is still decided by the card held at the end.

- **Drunk never skips.** A Drunk (or a Doppelganger who copied the Drunk) who runs out of time, or is gone past the grace period, is swapped by the server (`services._timeout_action`): center index from `drunk_timeout_center_index(random_seed, player_id, 3)` (a dedicated `random.Random` seeded from the game seed, the label `drunk-timeout` and the player id), resolved when the window closes like a chosen swap, same result sent (`{"card_index"}`), logged as a normal `swap_with_center` entry with `"made_by_server": true`. The prompt offers only `swap_with_center`; a `skip` is refused.

- **Results** are stored per window (`night_action_data["wave_<window>_result"]`); a player gets at most one in window 2.

**Action types:** `peek_player`, `peek_center`, `swap_with_player`, `swap_with_center`, `swap_others`, `see_team`, `none`, `skip` (explicit "do nothing": Seer, Robber, Troublemaker only, including a Doppelganger follow-up as one of them; advertised in the prompt's `action_types`; never for the Drunk, the Doppelganger's first look, or view-only roles). Roles: the 12 of `docs/specs/onuw/roles.md`.

## Timers survive a restart (memory backend)

The stored `Game.phase_deadline` / `night_window_opened_at` are the truth. `services.recover_timers()` (never under the queue backend: `run_startup_recovery` returns at once) runs once at server start (`run_startup_recovery()`, called from `config/asgi.py`; it runs in a short-lived joined thread so it works even when the server imports the app inside a running event loop, and closes that thread's DB connections; switched off by `ONUW_RECOVER_TIMERS_ON_START = False` in the test settings, never runs in migrations or management commands, tolerates an unmigrated DB). It does NOT reset presence (`apps/core/README.md`), opens a night that crashed before its first window, calls `ensure_timers(game)` for every game in night / discussion / voting, then `timers.rearm_from_table()` re-arms every other stored timer (presence checks) that has no thread here. `ensure_timers` re-creates what is missing (`timers.is_scheduled(key)` is the cheap check): the phase or window timer (a deadline that is overdue or less than `RECOVERY_RECONNECT_ALLOWANCE_SECONDS` = 15 s away is first moved to now + 15 s and persisted, so phones can reconnect before the vote is revealed or the night closes; the same happens in the lazy path only when the timer is genuinely missing; the extension depends only on the clock, so the fixed Doppelganger window's length still says nothing about her), the night's deferred "everyone acted, minimum length not passed" close (due at the minimum, not the deadline), and dropped players' grace timers. The Doppelganger window only ever gets its fixed deadline. `GameMeView` calls `ensure_timers` on every fetch, so a game also repairs lazily. Safe in several workers: every callback locks the Game row and checks the phase, and the night callbacks check the window number (`_auto_advance_wave`), so a stale window-1 timer cannot close window 2. A minimum-length (deferred) close re-checks readiness under the lock when it fires (a player treated as gone may have come back); if the window is no longer ready it puts the normal deadline timer back, and a reached deadline always closes. A phase with no deadline (`discussion_seconds`/`voting_seconds`/`night_wave_seconds` = 0) has no timer by design: only the host (or, for the vote, the last voter) moves it.

## Missed night results and the ack

**Missed night results.** `GET /me/` has `night_results`: the caller's own results for closed windows, `[{"wave", "action_type", "revealed_info"}]`, built from the night log by `services.client_action_result` (the same transform the `action.result` socket event uses) so the two cannot drift. One entry per result in window order (a Doppelganger with a follow-up gets two in window 1), skips omitted under protocol 1 (protocol 2 lists the caller's own, see "Night protocol 2"), nothing for a window still open (including her early look), nothing of anyone else's.

**Night results ack.** `GET /me/` has `night_results_seen` (the caller's own count, `PlayerRole.night_results_seen`); `POST /api/onuw/games/<id>/night-results/seen/` with `{"seen": n}` (a plain JSON integer 0-10, else 400 `bad_request`; 404 unknown game, 403 not a player) answers `{"night_results_seen": <stored>}`. `services.acknowledge_night_results` clamps `n` to the number of `night_results` the caller can see NOW (the Doppelganger's look is sent by socket while window 1 is open but listed only once it closes, so an early ack cannot cover it) and raises the stored count with ONE `UPDATE ... SET n = GREATEST(n, :value)` (no Game lock, never lowers). The client shows `night_results[night_results_seen:]` and acks after each window's dawn screen, sleepers too. `tests/onuw/test_v2_payloads_no_leak.py` sweeps the v2 payloads for foreign role names.

## Lock-in voting

`POST .../vote/` takes `{"target_player_id": <JSON integer>, "lock": <bool, default true>}` (anything else is 400 `bad_request`: no coercion). A vote is *picked* (`PlayerRole.vote_target`, `has_acted` false, changeable, NO socket event at all) and then *locked* (`has_acted`, final; any pick or lock after it is 409 `vote_locked`, except, under protocol 2, the SAME lock again (a resend whose answer was lost): `{"status": "submitted"}`, nothing stored or sent). Answers: locked `{"status": "submitted"}` (today's shape), picked `{"status": "picked", "target_player_id": N}` (the stored target). Under protocol 2 the body also names the `stage` (see Stages below). Errors carry `code` (`wrong_stage`, `wrong_phase`, `invalid_target`, `bad_request`, `vote_locked`; `detail` of a 400 from the service stays a LIST of messages as it always was). `services.submit_vote(game, voter, target, *, lock=True)` is ONE transaction: Game lock, phase re-checked, voter's PlayerRole lock, validate, store; a lock sends the group `progress {stage: "vote", done, needed}` (counts of the players not gone past grace) after commit (the original night also sends the legacy `vote.submitted` (who); **protocol 2 never announces who locked**, and its players list has no per-player `has_voted`), then reveals if `_votes_ready` (so two last locks reveal once and a vote cannot land after the reveal). **At any reveal every stored pick counts, locked or not** (`reveal_votes` reads `vote_target` for everyone; a dropped player's pick and an unlocked Hunter's pick count): it is a rule of the spec (`voting-and-resolution.md`), not an accident. `progress` is also sent when the vote opens (`done` 0) and when presence changes `needed` (`_evaluate_presence`). `/me/` has, under protocol 2 only (nothing is even computed for the original night), `player_id` (the caller's own id), `stage`, `my_vote` (the caller's own `{target_player_id, locked}` while voting, else null), `ready` (own flag, at the look stage and in the talk) and `progress` (`services.stage_progress`). The debug oracle has `vote_locked` per player next to `votes`, and `ready` per player.

## Ready to vote (the talk)

`POST .../ready/ {"ready": <bool>, "stage": ...}` (`ReadyView`, `services.set_ready`; strict bool else 400 `bad_request`; 403 not a player; 409 `wrong_stage` outside the talk and the look stage, or for a stage that is over) toggles `PlayerRole.phase_ready` (reset by `transition_to_discussion`) and answers `{"status": "ok", "ready": <stored>}`. One transaction (Game lock, PlayerRole lock, phase re-checked): every tap recounts `needed` (players not gone past grace) and sends `progress {stage: "talk", done, needed}`; when `done == needed >= 1` it calls `end_discussion`, the host button's own function, so a tap racing the host or the talk's deadline ends the talk once (the loser names a stage that is over: 409 `wrong_stage`). The talk never WAITS: readiness can only end it early, and there are NO grace timers in the talk, so a talker who went away is only left out of `needed` on the next tap; a phone that had been gone past grace coming back sends the new count (`register_connection`) but never ends the talk.

## Look stage (`card_look_seconds`)

A game setting, 0 to 120, default 0 = off = the deal opens the first window as before; **above 0 it needs `night_protocol` 2** (refused at the lobby and at the deal otherwise). When > 0 the deal (`services.begin_night`, called last by `GameStartView._deal`) does NOT open a window: the game stays in night, window 0, with `phase_deadline` = now + the setting (`_in_look_stage`: night, window 0, a deadline set) and a `card_look` timer (key `<game id>:look`, scheduled ONLY when the setting is > 0, so an old instance never gets a job it cannot run), and sends `progress {stage: "look", done: 0, needed}`. Every phone taps `POST .../ready/ {"ready": true}` (`false` is 400 `bad_request`: looking is one way); `ready` at any other window is 400 `wrong_phase`. The night opens (`start_night_phase`, idempotent under the Game lock, which also cancels `<id>:look`) when every player not gone past grace has looked, when the backstop fires, or when the host taps advance-wave (`advance_wave` at window 0 opens the first window; it used to raise). A tap that loses the race to the backstop names a stage that is over (409 `wrong_stage`). **One readiness rule:** `_stage_is_ready` (look and talk: `needed >= 1` and `done == needed`) and `_advance_stage_if_ready` are used by `set_ready` (a tap), `_evaluate_presence` (a grace period ended, a phone came back: it re-checks, else re-announces the count) and `ensure_timers` (the look timer was lost: if everyone present has already looked it opens the night, else it rebuilds `:look` with the reconnect allowance). `_night_start_is_stuck` only applies when there is no deadline (a look stage is waiting for taps, not stuck), and `recover_timers` does not open a window-0 night that has a look deadline. `advance-wave` accepts `{"from_window": n}` (0, 1 or 2; absent = no check) under the original night and answers 409 `wrong_window` when the game is in another window; under protocol 2 it names the `stage` instead (409 `wrong_stage`). The debug fire-timer accepts `key: "look"`; `current` already finds it. `/me/` `progress` is `{"stage": "look", ...}`, `ready` is the caller's own flag, `deadline` is the look deadline, `action_prompt` is null for everyone.

## Night protocol 2

**Night protocol 2 (`settings["night_protocol"] == 2`): every phone sends a `choose`.** The whole protocol-2 night lives in `apps/onuw/night2.py` (choose storage, the prompt, the one group event, the close rule) and `apps/onuw/protocol.py` (the switch `is_choose_night` and the stage tokens), behind a few narrow hooks in `services`; games without it (the default, and every game the old screens deal) keep the per-role night ("The night: two windows"), untouched, and `night_protocol` must be 1 or 2 (validated at the lobby and at the deal). Under 2: `POST .../action/ {"action_type": "choose", "picks": [...], "chosen": n, "stage": ...}` from EVERY player, 0 to 2 distinct ordered picks (`{"player_id": n}`, `{"center_index": n}`, `{"self": true}`; a pick of your own id is `self`). The PURE `engine/choose.py` parses the picks (`parse_picks`: malformed = not a list, over 2, an item that is not exactly one known key with a plain JSON integer / `true`, a stranger, an off-board centre index, a duplicate) and reads them per role (`interpret_choice`: Seer two centre picks or the first other player; Robber the first other player; Troublemaker two other players; Drunk the first centre card; a LONE Werewolf the first centre card; the Doppelganger's look the first other player; everything else nothing; the first valid action in tap order, "You" never a target). A pick that reads as nothing is NOT an error: it is stored as "chose, nothing valid" and the window close applies the role's timeout default (a Drunk is swapped by the server with `made_by_server`, team views and the Insomniac still happen, a lone Werewolf still learns it is alone, Seer / Robber / Troublemaker / the look skip). A Doppelganger's follow-up is read as the copied role. **One look:** her FIRST choose in window 1 is her look whatever it holds; if it holds no other player she has not copied and her second choose does nothing. **Identical answers:** every choose is `200 {"status": "submitted"}`; the only refusals are `wrong_stage` (409: the request names a stage that is over, including the look stage), `already_chosen` (409: a phone may send two chooses in window 1 and one in window 2; phones send ONE, only the Doppelganger a second, and the server takes a second from anyone so its ANSWER is no tell, though her extra request is visible on the network, an accepted tell; 409 only for a choose answering a prompt that is used up) and `bad_request` (400, malformed; any other `action_type` too), none depending on role (403 for a stranger). **Resends:** every choose carries `chosen`, the prompt's `chosen` it answers (required: missing / not a plain non-negative JSON integer = 400 `bad_request`); under the Game lock, after the stage check, `chosen` LOWER than the stored count is a resend of a choose already taken (its answer was lost): the same 200, nothing stored, read or sent; higher = 400 `bad_request`; equal = a new choose. So a 200 only says the server holds a choose for the prompt named (a choose built from a stale prompt is answered 200 and stored nowhere): after ANY choose the phone re-reads `/me/` and trusts `chosen` / `chooses_left`. Without it a resent look was counted as the Doppelganger's second choose and read as her follow-up (found by the model in `docs/dev/models/night2/`). Every other protocol-2 request is safe twice by what it does or because its first copy ended the stage (`tests/onuw/test_resend.py`; table in `docs/specs/onuw/api-contract-v2.md`, "Third amendment"). **Own results (protocol 2 only):** a `peek_center` result has `center_indices` (in the order of `roles`); a result that is the role's default because the picks meant nothing (or there was no choose) has `"nothing_chosen": true`: the caller's own `skip` entries are listed (`{"nothing_chosen": true}`), the Drunk's server swap and a lone Werewolf with no centre card carry it too (`services._transform_revealed_info`, `choose_night=True`). The count is `night_action_data["chose_<window>"]` (no new column; kept by `persist_wave_results`). **Events:** a window opens with ONE group event `night.window {window, deadline}` (client `night_window`) and closes with the group `wave.complete`; there is NO per-player event in the night at all (no `action.prompt`, `wave.waiting`, `action.result`; the Doppelganger's look is not sent either). **`GET /me/`:** `action_prompt` is present for every player in an open window with one shape (`engine.choose.build_choose_prompt`: `window`, `kind` = `none|seer|robber|troublemaker|drunk|lone_werewolf|doppelganger_look`, `role_acting_as` (your own), `shapes` (which picks would do something, as data: alternatives such as `[{"players":1},{"center":2}]`, `any` = one card of the board; picking "You" or nothing always does nothing; the server's reading stays the authority, a pick outside the shapes safely does nothing), `action_types: ["choose"]`, `max_picks`, `max_chooses` (what the server ACCEPTS: two from anyone in window 1), `chosen` (echoed by the next choose), `chooses_left` (0 or 1: what this phone should still send; 1 again only for the Doppelganger's armed follow-up, which her own `kind` already says; `engine.choose.chooses_left`), and the same board for everybody; no teammates; a lone Werewolf's `kind` states its real option), and `night_results` lists the Doppelganger's look as soon as it resolves (her own, while window 1 is open). `revealed_info` role names are canonical (`"Werewolf"`) instead of lower-cased, `copied_role` as always. **Closing (every stage ends the moment everyone present has done their part; nothing adds to a table's settings):** look = all ready; talk = all ready; vote = all locked; window 2 = every present phone has chosen, subject to the EXISTING `night_min_window_seconds`; window 1 stays fixed-length (the table's own `night_doppelganger_window_seconds`, whatever it is; the server changes no default or minimum of it); window 2 closes when EVERY present phone (not gone past grace; a phone still inside grace holds it) has chosen once, never before `night_min_window_seconds` (via `_close_or_defer`), else at the deadline, so the close time cannot say who had a choice. `ONUW_ALLOW_UNTIMED_NIGHT` (base False; True in the test, development and harness settings) gates protocol-2 games with `night_wave_seconds` / `night_doppelganger_window_seconds` of 0 or `night_min_window_seconds` under 5: refused at the lobby and at the deal where it is False. With the fixed Doppelganger length off (dev only) window 1 ends when every phone has chosen once (a Doppelganger who copied a role with a follow-up is waited for until she has sent it).

**Stages.** `GET /me/` carries an opaque `stage` under protocol 2 (`protocol.stage_token`: look, `w1`, `w2`, talk or vote plus a piece of the GAME's id, so a token from an earlier game, even the same stage after play again, never matches). `choose`, `ready`, `vote` (pick and lock) and the host's `advance-wave`, `end-discussion` and `reveal-votes` must send it back (missing or not a string: 400 `bad_request`); a request for a stage that is no longer the game's is `409 {"detail": "That stage is over.", "code": "wrong_stage"}`, the same for every role and every endpoint, decided under the Game lock (`protocol.require_stage`), storing nothing. So a late tap can never land in the next stage (a Robber's late window-1 choose used to be stored as his window-2 action). Protocol 1 has no stages (`from_window` stays its check).

**What differs between roles in a `choose` request (documented, and visible only to someone timing the network; the app's rule is that a phone changes what others can see immediately on tap, never on the response).** `night2.submit_choose` does the same work for every caller: lock the Game, check the stage, lock the caller's row, build the game state, parse the picks against the table, read the caller's acting role, store the picks and count them, and run the close check in the SAME transaction. Measured on the test database (queries per request): 11 for every role in window 2 and for every other player in window 1; a Doppelganger's FIRST choose in window 1 costs 18, the 7 extra being her look resolving in her request (`services._resolve_doppelganger_look`: it needs her copied role for her follow-up). `persist_wave_results` writes only the rows that changed.

## Automatic deck and create defaults

Lobby settings may say `deck: "auto"` (or `"custom"`) and `deck_chip` (`simple|classic|chaos`, default simple; validated at PATCH and deal). With `auto` the host's card list is ignored and the DEAL (`GameStartView._deal`, under the Lobby row lock) builds the deck for the players at the table now from `engine/decks.py` `DECK_TABLE` (3 to 10 players x 3 chips, each exactly players + 3 legal cards) into the GAME's settings only: the lobby keeps saying `auto`, so play again with one more player deals the next row. The doc table in `docs/specs/onuw/recommended-setups.md` ("Automatic Decks") is compared with `DECK_TABLE` by `tests/onuw/test_auto_deck.py`, which also checks all 24 rows are legal decks. `POST /api/lobbies/` takes an optional `defaults: "v2"` (any other value: 400 `bad_request`) that `GameHooks.default_settings` answers with `hooks.V2_DEFAULTS` (`card_look_seconds` 30, `night_protocol` 2, `deck` auto, `deck_chip` simple, and NOTHING else: no timer length and never the Doppelganger's window, which stay the table's own settings or the server's existing defaults); settings given in the body win; without `defaults` nothing is written. The merged settings are validated at create (400 `bad_request` with the errors).

## Night timeline (results)

`GET .../results/` (results phase only, members only, as before) has `night_timeline`: `{seats, cards, dealt, steps, final, center_moved}` built by the PURE `engine/timeline.py` (`build_night_timeline`) FORWARDS from the dealt cards (`PlayerRole.original_role` by seat, `Game.dealt_center_cards`) and `Game.night_actions_log` (`ActionLogEntry.to_dict` is the one log format). Cards have stable ids (`k0..k<n-1>` by seat, then the three centre cards) and a server-set `werewolf` flag (a Werewolf card, or a Doppelganger card whose holder COPIED Werewolf: it is a werewolf card for whoever ends the night holding it, `docs/specs/onuw/doppelganger.md` Team Resolution Rule); each step is one log entry in WAKE order (the engine resolves team views in SEAT order, so inside order group 2 the timeline re-sorts to Werewolves, Minion, Masons with a stable sort; team views move no cards; `see_team` rows of one role in one group merge into ONE step with all its actors, dealt ones first, a Doppelganger who copied the role among them and named in `doppelganger_actors`; a Doppelganger-Minion acts in window 1 and keeps her own step) with `actors`, `doppelganger_actors`, `action` (`copy`, `see_team`, `peek_player`, `peek_center` (a lone Werewolf's look too), `swap_with_player`, `swap_others`, `swap_with_center`, `look_own`, `skip`), `looked_at` (card ids as the table was at that step), `moves`, `team`, `copied_role`, `made_by_server` and `positions_after`. A game dealt before `dealt_center_cards` recovers the centre with `recover_dealt_center` (undo the logged swaps from the final table and require the players' cards to equal their dealt roles). The undo checks ONLY that the players' cards come back to their dealt roles (the centre it returns is what the log implies). `services.night_timeline_for` is a presentation boundary: ANY failure answers `night_timeline: null` so the rest of the results still show; a refusal for a game from before the centre was stored is logged once at WARNING, anything else at ERROR. The proof is in the tests, not a runtime self-check: the replay's final table equals the engine's for all 29 reference games and 1500 seeded random nights, with the actions collected the way the server collects them (`tests/onuw/night_rules_reference.engine_night`: seat order, a Doppelganger's follow-up last) and seats the reverse of player-id order (`tests/onuw/test_night_timeline.py`).

## Debug affordances (DEBUG only)

For the integration harness there are `DEBUG`-gated affordances (all 403 in production, each with a rejection test): a forced-assignment / seed override on game start (`GameStartView`), a `debug-state` full-state oracle (its `connected` is real socket presence; `pending_timers` lists the armed timers), and a `debug-fire-timer` hook (`wave:1` / `wave:2` close that night window now; `current` ignores grace timers) — see `apps/onuw/debug.py` + `debug_views.py`. Game timers are per-game settings, so the harness and `tools/game_driver.py` set `night_min_window_seconds`, `night_doppelganger_window_seconds` (and the other timers) to 0 for speed. Boot the harness backend with `just harness-serve` (`config.settings.harness`: `DEBUG=True`, throwaway DB `midnight_village_harness`, `127.0.0.1:8001`). `tools/game_driver.py` is a CLI that drives a whole ONUW game through these. Full docs: `docs/dev/debug-harness/`.
