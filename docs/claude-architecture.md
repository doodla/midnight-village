# Claude Code setup

What `.claude/` enforces, so agents do not have to remember it. Update this file in the same
commit as any change under `.claude/`.

## The commit gate: git's own hooks (`.claude/hooks/git/`)

The gate only catches the embarrassing things, in seconds. GitHub is the wall: it runs every
check on every pull request (next section). Enabled by `git config core.hooksPath .claude/hooks/git`
(shared by every worktree of the clone), which `.claude/hooks/session-start.sh` sets at the start of every
session (and `tool/setup_env.sh` calls). The Bash guard blocks a commit while it is not set and
says to run that script. The hooks check what git is really about to commit, however the commit
was typed (`-a`, pathspecs, `-C`, global options):

- `pre-commit`: the instruction link check on the staged text (`--staged`), then the fast
  checks the commit's paths need (`git diff --cached --no-renames`, so a file moved out of code
  still runs its checks), in parallel. `pre-merge-commit` runs the same for a merge git commits
  by itself, on everything the merge changes; a merge with conflicts is finished with
  `git commit`, which runs `pre-commit`; a fast-forward makes no commit.
- `commit-msg`: the subject reads `type(scope): description` (git's merge and revert subjects pass).

Routing and what each block runs (`.claude/hooks/lib/gate.sh`, mode "fast"):

| Paths | Block | Fast checks |
|---|---|---|
| `backend/**` (not Markdown), `docs/specs/onuw/recommended-setups.md` | backend | the root `just check` (its steps: `just --show check`) |
| `frontend/**` (not Markdown) | frontend | `just analyze`, `just flutter-format-check` |
| `contract_samples/**` | backend, frontend | both of the above |
| `.claude/**` (not skills), `tool/**`, `.github/**`, `docs/dev/main-ruleset.json`, root `justfile` | guardrails | `just test-guardrails`: guardrail, gate-routing and workflow tests |
| Markdown, `docs/**` | none | only the link check (under a second) |
| anything else | backend, frontend | both of the above |

A block that already passed on the same inputs (its files, `backend/.env`, the root `justfile`,
tool versions; recorded in the git dir for 14 days) is not run again; a `just gate-full` pass
counts. A block is stopped after 100 s, which blocks. A broken or missing `gate.sh` blocks every
commit. No test suite runs in a commit, so a commit needs no long Bash timeout.

`just gate-full [backend|frontend|guardrails ...]` (`.claude/hooks/gate-full.sh`, mode "full") runs every
required GitHub check that can run here, in parallel, with times, and ends by naming the ones only
GitHub runs (`GATE_FULL_SKIPS` in `.claude/hooks/lib/gate.sh`). A pass is recorded.
`.claude/guardrails/tests/test_gate_full.py` holds its steps and that list to the workflows, and that a
recipe of `backend/` or `frontend/` found at the root means the same there (`check-backend`,
`test-backend`, `flutter-test`, `flutter-format-check` carry the folder's own meaning).
An old name stays in its folder as a stub in the `renamed` group (`cd frontend && just test` fails
with `renamed: just flutter-test`), never falling back to the root's recipe of that name: the test
reads the group as the rename table, and fails a name a folder had on main that it no longer has.
`.claude/hooks/test_gate_routing.sh` checks routing and that a commit runs no suite.

## GitHub: the wall (`.github/workflows/`)

Every check runs on every pull request to main (and on each push to main), as parallel jobs that
only call `just` recipes. `.claude/guardrails/tests/test_workflows.py` fails when a workflow names a
recipe that does not exist, a check workflow filters on paths (a required check that never starts blocks the
merge for ever) or has a job with no name or time limit.

Not part of the wall, and told in `docs/dev/deploy-vercel.md`: `android-download.yml` (the
Android app's rolling release), `deployed-check.yml` (after each merge: `tool/promote_live.py`
moves `live-server` and `live-app`, then `tool/deployed_check.py` proves the live server and app
work together), `live-watch.yml` (the same check every 6 hours), the live-branch rulesets in
`docs/dev/rulesets/` rehearsed by `live-rehearsal.yml`, and the way back, `just revert-release`.
Their rules are held by `.claude/guardrails/tests/test_workflows.py` (`WorkflowPublishing`,
`WriteTokens`, `WorkflowAfterMerge`), `test_promote_live.py`, `test_release_workflows.py`,
`test_revert_release.py`, `test_release_assets.py` and `test_deployed_timing.py`; the wall's rules
above apply to every other workflow.

**What a change is compared with.** `tool/change_base.py`: the main the change was built
on (on a pull request the merge's first parent, elsewhere where the branch left main),
never main as it is now, so main moving under a running check is not blamed on the
change (`.claude/guardrails/tests/test_change_base.py`). The file-size, guard-edit and
previous-build checks all take it from there.

**Words added.** `tool/words_added.py` (the same step as the guard lines, `just guard-edits`)
compares every copy key with the main the change was built on; a copy class with more words
than it had needs a line under `Words added` in the pull request's description. It replaces
the pinned per-screen word budgets (`.claude/guardrails/tests/test_words_added.py`).

**File sizes.** `tool/check_file_sizes.py` fails `just check`, the commit gate (on what is
staged) and `just gate-full` when a source file passes 600 lines: a file that long cannot be
read whole, and two branches that touch it collide. A file already over it on main may stay
or shrink but not grow: move something out first, then add. There is no list: the check
compares with main on the remote (fetched when a shallow checkout lacks it), so only the change
that adds to a long file fails. Tests and generated code are not counted
(`.claude/guardrails/tests/test_file_sizes.py`).

**Guards.** A test that holds a rule for the whole app carries `Guard file` in a comment at
its top (no list: a new guard joins by carrying the line). `tool/guard_edits.py`
(`just guard-edits`, a step of GitHub's "Backend Checks") fails a pull request that edits one
unless its description has a line `- <file name>: <why>`; locally it only reminds
(`.claude/guardrails/tests/test_guard_edits.py`; a changed binary file, a golden picture, is never
read: a guard is a text file). `just check` also lints `tool/` and the hooks for
errors swallowed in silence (`just lint-tools` in `backend/`).

**Disk.** `tool/tidy.py` gives the disk back: a quiet worktree loses its build output (the
session-start hook runs it), and `just tidy` removes one whose branch was merged and that holds
nothing uncommitted; a helper's worktree is never removed by it (its docstring;
`.claude/guardrails/tests/test_tidy.py`).

**Words.** The app's copy has one home, `frontend/lib/design_system/copy/`. `tool/copy_page.py`
makes a page of every key on demand (`just copy-page`) and, in `just check`, fails a spec that
names a key that does not exist or quotes a key's words (its docstring;
`.claude/guardrails/tests/test_copy_page.py`).

**Starting and handing over.** `just brief <screen>` (`tool/brief.py`) and `just brief <area>`
(`tool/brief_areas.py`, the table; `just brief` lists them) print what a builder needs from the
sources themselves. `just handover <file>` (`tool/handover.py`) is the one way to hand over: it
refuses work that is not committed, pushed and mergeable, runs what the change reaches, says
which of GitHub's checks ran here ("READY (N of M of GitHub's checks run here)", never "GitHub
will pass"), draws the reached states beside main on contact sheets, and writes one fixed shape.
What each does: its docstring (`.claude/guardrails/tests/test_brief.py`, `test_handover.py`,
`test_github_checks.py`). A red test run ends with what failed (`tool/failed_tests.py`). Every
recipe of `frontend/` and `backend/` also exists at the root: `tool/root_recipes.py` fails a
change that adds one without, and `--fix` writes the line
(`.claude/guardrails/tests/test_recipes_everywhere.py`).

**What an agent must read.** `tool/context_budget.py` (in `just check` and the commit gate)
measures, in tokens, each CLAUDE.md, each brief, each role's read-first path (the CLAUDE.md
files it works under, its agent definition, every tracked text file those or its brief say to
read, of any kind, and the brief), each file of our own skills (1,000 each: a skill is read
whole when called) and the whole instruction surface (the Markdown, and what a
role path reads besides); a read file that is binary or ignored by git fails. It holds each to a limit as the file sizes are
held: under it on main, it may not pass it; over it on main, it may not grow. The limits are
constants at the top of the tool; `--report` prints every measure beside main's. A brief is
measured from its documents alone, its code lists counted at their caps (`CODE_CAPS`), so no
Flutter is needed (`.claude/guardrails/tests/test_context_budget.py`). The screen and
design-system briefs quote every rule of `frontend/docs/app-rules.md` (each is in bold there).

**Instruction links.** `tool/check_instruction_links.py` (in `just check`, and on the staged
text in the commit gate) reads every tracked Markdown file but third-party skills: a path with a folder
in it is read from the repo root (`./` and `../`, and Markdown links, from the document), a bare
name is in the document's folder or names one file, a quoted section after a path is one of its
headings, a `just` recipe exists; a word in prose that starts with a top folder and a slash is a
path too. `--fix` rewrites a path that has one reading from elsewhere
(`.claude/guardrails/tests/test_instruction_links.py`).

**Facts about the code, from the code.** `tool/gen_docs.py` (in `just check`; `--fix` writes)
fills every `generated by tool/gen_docs.py` block: the commands of the CLAUDE.md files (each
recipe's own comment, and the steps of a recipe that is only steps), the screens and the sizes
they are judged at, the required checks and the agents tables below. A block that is not what
the code says fails, with the fix.

**The heavy queue.** `tool/heavy.py` (`just heavy <command...>`, `just heavy --status`): every heavy
command waits for one of a few slots, so the machine is never asked for more than it has (how,
and how the count was chosen: its docstring; `.claude/guardrails/tests/test_heavy.py`).

**As GitHub's backend job runs it.** That job has no Flutter, so `just test-guardrails` runs its tests with Flutter and Dart
off PATH (`tool/path_without.py`; `.claude/guardrails/tests/test_path_without.py`): a test that runs them fails on a builder's
machine too, not only on the pull request (the first run of the heavy-queue change did, in a brief of a screen).

**A rule holds per change.** A check that reads the whole tree can be passed by two pull
requests separately and fail once both are merged, for a builder who did neither. So a rule
compares a change with the main it was built on (`tool/change_base.py`, or the merge base in
a Dart test) and fails only for what that change did: file sizes, guard edits, root recipes,
the to-do list of unswept states, raw values, removed assets. What cannot be made so (two
changes that break each other's code or re-record the same samples) is caught by main's own
run after each merge, and said: `.github/workflows/main-red.yml` (`tool/main_red.py`) opens
one issue, "main is red", naming the check and the merge, adds to it while it is red, and
closes it when main's newest runs have all passed (`.claude/guardrails/tests/test_workflows.py`).

**The built web app, once.** `frontend/tool/web_build_cached.sh` gives a tool the folder of a finished web build and builds again only when what goes into it changed.
`.claude/guardrails/tests/test_web_build_cached.py` holds that with a stand-in for the build: built once, again on a changed source or argument, nothing left by a failed build, the newest four kept.

**Lines of the notes.** `tool/doc_lines.py` (in `just check`) fails a prose line over 200
characters in a tracked note (two branches that add a word to it clash) and `--fix` reflows it,
changing line breaks only (what it leaves alone: its docstring;
`.claude/guardrails/tests/test_doc_lines.py`).

**The fast check.** `just piece-check` (`tool/piece_check.py`) is what a builder runs between
edits: the fast checks, the backend tests, and only the app's tests and screen states that can
see the change, found from imports and widget trees, never listed (what it runs: its docstring;
`.claude/guardrails/tests/test_piece_check.py`). It ends with the lines the pull request's
description must carry. GitHub still runs everything.

`.claude/guardrails/tests/test_checkout_whole.py` keeps a fresh checkout working as it stands: every
shell script parses (`bash -n`), the lint and type tools in recipes and hooks are run as
`uv run --group lint <tool>` (the version in `uv.lock`, never one from PATH), and
`tool/ensure_env.sh` writes a missing `backend/.env` and leaves an existing one alone
(the harness's backend recipe calls it too, and reads what it wrote).

The ruleset `docs/dev/main-ruleset.json` is what makes this the wall: a pull request on the
default branch, squash merges only, every check above required (up to date with main not
required, so two sessions do not block each other), no force pushes or deletion, nobody
bypassing. It is on: the owner imported it (GitHub reports main as protected, checked 23 November 2026).
To import it again: Settings, Rules, Rulesets, New ruleset, Import a ruleset, choose the
file; or as a repository admin:

```bash
gh api -X POST repos/doodla/midnight-village/rulesets --input docs/dev/main-ruleset.json
```

When a check is added, renamed or removed, change the job's `name:` and the ruleset file in
the same commit (`.claude/guardrails/tests/test_workflows.py` fails until they match), then import the
file again (delete the old ruleset first, or edit its checks in the settings).

## Adding a check

A check every agent runs into costs every agent, so a new one is accepted only when it:
1. tests the promise, not the shape of the last bug;
2. comes with a recorded break it catches (the prove-guards command, being built on branch
   `guard-teeth`, will run them);
3. prints `file:line: what is wrong. Fix: <command or edit>`;
4. takes its cases from a registry or the code where one exists, not a list kept by hand;
5. has no allowlist kept by hand that can grow.

A check that cannot meet these is not added: say so instead.

## Claude Code hooks (`.claude/settings.json`; timeouts in seconds)

Every hook command starts from `$CLAUDE_PROJECT_DIR`, never a relative path:
a session whose shell sits in `backend/` or `frontend/` must still find the script.
A Bash guard whose script is missing lets the command run and warns (the git hooks are the gate).

| Event | Script | Does |
|---|---|---|
| PreToolUse Agent, Task, Workflow | `.claude/guardrails/runner.py` | Blocks a subagent not pinned to `opus`, `sonnet` or `haiku` (on trial) with an effort, and forks. |
| PreToolUse Bash | `.claude/hooks/git_guard.py` | Stops the commands that would skip the commit gate (`--no-verify`, a changed hooks path, a push to `live-server` or `live-app`, and the rest its docstring lists), reading the command as the shell would (`.claude/hooks/shell_text.py`). Not a wall: GitHub is. Tests: `.claude/guardrails/tests/test_git_guard.py`. |
| SessionStart startup, resume, compact | `.claude/hooks/session-start.sh` | Sets `core.hooksPath` to the git hooks if it is anything else and makes the hooks executable; starts Postgres when it is installed and down; warns when the checkout is behind the remote's main (every hook, guard and instruction comes from it) and when a hook script the settings run is missing; otherwise silent, one line if it cannot set the gate, never fails the session. A fresh container's tools come from `tool/bootstrap_container.sh` (`docs/dev/environment.md`), not from this hook. |
| PreToolUse Bash | `.claude/hooks/poll_guard.py` | Refuses a sleep loop that waits on another job and says what to do instead: start it once with `run_in_background` (what counts: its docstring). A reminder, not a wall; fails open. Tests: `.claude/guardrails/tests/test_poll_guard.py`. |
| PostToolUse Edit, Write | `.claude/hooks/post-edit-format.sh` | Formats the edited `.py` (the ruff in `uv.lock`: `uv run --group lint`, never one from PATH) or `.dart` file. |
| Stop | `.claude/hooks/verify-done.sh` | With uncommitted `.py`/`.dart` work, runs the fast checks it touches (as the commit gate does), unless they already passed on the same inputs. No test suite. |

## Guardrails (`.claude/guardrails/`)

`runner.py` runs the rules in `config.toml` (deny or warn only). The one rule,
`subagent_model_effort`, keeps subagents off the main session's model for cost. Its message points at
`docs/dev/running-the-work.md`, which holds how to choose a model and effort. Adding a
rule: `.claude/guardrails/README.md`. Tests: `just test-guardrails`. A test or check that scans
repo files reads them from `tool/repo_files.py` (the files git tracks or does not ignore), so a builder's
worktree copy under `.claude/worktrees/` is never scanned.

## Skills (`.claude/skills/`)

Our own: `correct` turns a mistake that happened into a check that would have caught it (or
says no honest one exists). In `no-comments` one haiku per file proposes (`sorter.md`);
`tool/comment_rows.py` checks the answers and deletes only what `tool/empty_comments.py` proves
says nothing (`.claude/guardrails/tests/test_comment_rows.py`, `test_empty_comments.py`). Adapted from pstack, MIT: `.claude/skills/NOTICE`.
A skill whose front matter has no vendor's `metadata:` is ours (`tool/skills.py`): measured and
link-checked like any instruction. Builders and reviewers list `Skill` in their tools and name
the skill in the step that uses it, so it loads only when called (not `skills:`, which would load
it before the first edit); `test_agent_briefs.py` fails a named skill an agent cannot load.

Seven third-party `flutter-*` skills (Flutter's generic guides on animation, layout,
concurrency, HTTP and JSON, accessibility, testing, theming). Nothing here depends on them, and
where one disagrees with `frontend/CLAUDE.md` the CLAUDE.md wins.
