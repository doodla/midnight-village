## Work Package WP02: Auth & HTTP Infrastructure (Priority: P0)

**Goal**: Create the authenticated HTTP client with JWT bearer tokens and automatic token refresh — the foundation all authenticated API calls depend on.
**Independent Test**: Unit tests verify: (a) bearer token added to requests, (b) 401 triggers refresh then retries, (c) refresh failure redirects to auth screen.
**Prompt**: `/tasks/WP02-auth-http-infrastructure.md`
**Estimated Prompt Size**: ~400 lines

**Requirements Refs**: FR-001, FR-002, SC-004

### Included Subtasks
- [x] T006 Create `AuthInterceptor` in `frontend/lib/core/api/auth_interceptor.dart` — `QueuedInterceptorsWrapper` that adds `Authorization: Bearer <token>` header, handles 401 with refresh retry, signals auth failure
- [x] T007 Create `AuthenticatedClient` in `frontend/lib/core/api/authenticated_client.dart` — Dio wrapper with `AuthInterceptor` attached, exposes get/post/patch/delete matching `ApiClient` surface
- [x] T008 Create `authenticatedClientProvider` in `frontend/lib/features/auth/presentation/auth_notifier.dart` — `@Riverpod(keepAlive: true)` provider wiring `TokenStorage` and unauthenticated `ApiClient` for refresh calls
- [x] T009 Tests in `frontend/test/core/api/auth_interceptor_test.dart` — mock HTTP responses to verify bearer token injection, 401 refresh flow, concurrent request queueing, refresh failure redirect

### Implementation Notes
- Research decision R1 applies: Separate `AuthenticatedClient` avoids circular dependency. The unauthenticated `ApiClient` (existing) handles token refresh calls.
- Use `QueuedInterceptorsWrapper` (research R1) to serialize requests during refresh — prevents multiple simultaneous refresh calls when game state polling and WS reconnection trigger concurrent requests.
- On refresh failure: clear tokens via `TokenStorage`, set `AuthNotifier` state to `unauthenticated`. The GoRouter auth guard (WP04) handles redirect.
- Follow existing `ApiClient` pattern in `api_client.dart:12-29` for Dio setup, `auth_service.dart:81-110` for refresh call pattern.
- TEST_FIRST: Write interceptor tests first using mocktail to mock Dio responses.

### Parallel Opportunities
- T006 and T007 can be developed together (same concern).
- T009 tests can be scaffolded before implementation.

### Dependencies
- None — uses existing `ApiClient`, `TokenStorage`, `AuthService` providers.

### Risks & Mitigations
- Risk: Concurrent refresh race condition. Mitigation: `QueuedInterceptorsWrapper` serializes interceptor execution.
- Risk: Token storage async access in synchronous interceptor. Mitigation: `QueuedInterceptorsWrapper.onRequest` supports async handlers.

### Implementation Notes

- `GameNotifier` is the most complex piece. WS event → state mutation mapping:
  - `wave_start` → update `currentWave`, `deadline`; set `nightSubView` based on whether `action_prompt` arrives
  - `action_prompt` → if `actionTypes.length > 1`: `seerChoice`; if single: `actionPrompt`; update `roleActingAs` for Doppelganger. For Insomniac (self-targeted peek, no choice), auto-submit without rendering prompt
  - `action_result` → `actionResult` sub-view, store `lastActionResult`

  - `phase_change` → update `phase`, `deadline`
  - `vote_submitted` → mark player voted in `VoteProgress`
  - `vote_reveal` → compute tally, start 5s timeout for `game_results`
  - `game_results` → fetch full results via GET
- Doppelganger multi-step (FR-023): After first `action_result`, if copied role has immediate follow-up, server sends another `action_prompt` in the same wave. The notifier handles this naturally — each `action_prompt` event triggers the same state machine transition.
- `TimerProvider` uses `Timer.periodic` or `Stream.periodic`. Returns `null` when deadline is null.
- `GameContainerScreen` delegates to placeholder sub-views initially — real views added in WP08–WP10.
- TEST_FIRST: Notifier WS event tests first. Test each event type in isolation, then test event sequences (e.g., wave_start → action_prompt → action_result → wave_complete).
