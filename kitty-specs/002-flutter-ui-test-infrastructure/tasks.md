# Work Packages: Flutter UI Test Infrastructure

**Inputs**: Design documents from `/kitty-specs/002-flutter-ui-test-infrastructure/`
**Prerequisites**: plan.md (required), spec.md (user stories)

**Tests**: This feature IS test infrastructure — the deliverables are test frameworks, helpers, and example tests. Every work package includes validation tests as core deliverables.

**Organization**: Fine-grained subtasks (`Txxx`) roll up into work packages (`WPxx`). Each work package must be independently deliverable and testable.

**Prompt Files**: Each work package references a matching prompt file in `/tasks/` generated by `/spec-kitty.tasks`. Treat this file as the high-level checklist; keep deep implementation detail inside the prompt files.

## Subtask Format: `[Txxx] [P?] Description`
- **[P]** indicates the subtask can proceed in parallel (different files/components).
- Include precise file paths or modules.

## Path Conventions
- **Frontend**: `frontend/lib/`, `frontend/test/`, `frontend/integration_test/`, `frontend/tool/`

## Work Package WP01: Global Test Configuration & Deterministic Rendering (Priority: P0)

**Goal**: Establish the foundational test configuration that ensures deterministic rendering across platforms — font loading, screen sizing, golden file comparison, and platform-specific baseline management.
**Independent Test**: Run any existing widget test and confirm fonts load deterministically. Run `just flutter-test-golden` and confirm the command is recognized (even with no golden tests yet).
**Prompt**: `/tasks/WP01-global-test-config.md`
**Estimated Prompt Size**: ~350 lines

**Requirements Refs**: FR-001, FR-002, FR-003, FR-011, FR-013, FR-016

### Included Subtasks
- [x] T001 Create `frontend/test/flutter_test_config.dart` — global test config that loads bundled fonts (PlayfairDisplay, Inter) via `FontLoader` before any test runs; set as the project-level test configuration file
- [x] T002 Create `frontend/test/helpers/golden_test_helper.dart` — `pumpWithGolden` extension on `WidgetTester` that sets fixed screen size (390×844, iPhone 14 logical), injects deterministic theme, and calls `matchesGoldenFile` with platform-aware path
- [x] T003 Implement custom `GoldenFileComparator` in golden_test_helper.dart that routes baselines to `test/design_system/goldens/macos/` or `test/design_system/goldens/linux/` based on `Platform.operatingSystem`
- [x] T004 Extend existing `pumpWithTokens` in `frontend/test/design_system/test_helpers/pump_with_tokens.dart` to accept optional golden configuration parameters (fixed screen size, deterministic fonts) per FR-013
- [x] T005 Add justfile commands to `frontend/justfile`: `flutter-test-golden` (run golden tests via tag), `flutter-golden-update` (regenerate all baselines with `--update-goldens`)

### Implementation Notes
- `flutter_test_config.dart` must define a top-level `testExecutable` function — Flutter's test runner picks this up automatically
- Font loading uses `FontLoader` to load font data from `rootBundle` for each family/weight before any test runs
- The custom `GoldenFileComparator` extends `LocalFileComparator` and overrides `getTestUri` to inject the platform directory
- Golden test tag: add `@Tags(['golden'])` to golden test files so `flutter-test-golden` can filter via `--tags golden`
- `flutter-golden-update` uses `flutter test --update-goldens --tags golden`

### Parallel Opportunities
- T001 and T005 can proceed in parallel (different files)
- T002 and T003 are tightly coupled (same file)

### Dependencies
- None (starting package)

### Risks & Mitigations
- Font loading may behave differently in test vs runtime — verify with a simple rendering test before proceeding
- `flutter_test_config.dart` is project-global; ensure it doesn't break existing tests by making font loading additive

## Work Package WP02: Mock HTTP & WebSocket Layers (Priority: P0)

**Goal**: Build the shared mock service infrastructure that both integration tests and interaction harnesses depend on — a mock Dio HTTP layer that fails loud on unmocked endpoints, a fake WebSocket channel for game event simulation, and a timer control utility for countdown testing.
**Independent Test**: Mock HTTP returns canned responses for configured endpoints and throws on unconfigured ones. Mock WebSocket can inject events and capture sent messages. Timer control can fast-forward without real delay.
**Prompt**: `/tasks/WP02-mock-service-layers.md`
**Estimated Prompt Size**: ~450 lines

**Requirements Refs**: FR-005, FR-006, FR-008

### Included Subtasks
- [x] T006 [P] Create `frontend/test/helpers/mock_http_client.dart` — custom Dio `Interceptor` that matches request path + method against a registry of canned `Response` objects; throws `UnmockedEndpointException` on any unregistered request (fail loud per spec edge cases)
- [x] T007 [P] Create `frontend/test/helpers/mock_websocket.dart` — fake `WebSocketChannel` backed by `StreamController` pairs; exposes `addServerEvent(dynamic data)` for injecting server events and `List<dynamic> sentMessages` for capturing client-sent messages; supports `close()` lifecycle
- [x] T008 [P] Create `frontend/test/helpers/timer_control.dart` — utility wrapping `FakeAsync` that allows tests to advance time (e.g., `advanceBy(Duration)`) for countdown and auto-transition testing without real delays
- [x] T009 Write tests for mock HTTP in `frontend/test/helpers/mock_http_client_test.dart`: verify canned response return, verify throw on unmocked endpoint, verify path+method matching
- [x] T010 Write tests for mock WebSocket in `frontend/test/helpers/mock_websocket_test.dart`: verify event injection reaches stream listeners, verify sent message capture, verify close lifecycle
- [ ] T010a Write tests for timer control in `frontend/test/helpers/timer_control_test.dart`: verify `advanceBy(Duration)` advances fake time, verify interaction with `Timer` and `Stream.periodic` patterns, verify no real delay occurs

### Implementation Notes
- Mock HTTP interceptor pattern: `MockHttpClient.when(method: 'GET', path: '/api/v1/me/').thenReturn(Response(data: {...}, statusCode: 200))`
- WebSocket fake must implement the same interface the app's real WebSocket client uses — check `frontend/lib/core/` for the channel abstraction
- Timer control should work with both `Timer` and `Stream.periodic` patterns used in game countdown widgets
- The `UnmockedEndpointException` should include the method and path in its message for easy debugging

### Parallel Opportunities
- T006, T007, and T008 are fully independent (different files, different concerns) — all three can proceed in parallel
- T009 depends on T006; T010 depends on T007; T010a depends on T008

### Dependencies
- None (can proceed in parallel with WP01)

### Risks & Mitigations
- Dio interceptor API may change between versions — pin to Dio 5.9.x as already in pubspec
- WebSocket channel interface may not be fully abstracted yet in the app code — if not, create a minimal abstraction that the mock implements

## Work Package WP03: Golden Test Examples & Validation (Priority: P1) 🎯 MVP

**Goal**: Prove the golden test framework works end-to-end by writing golden tests for existing design system components. Validate the full generate → compare → update cycle and confirm deterministic output across runs.
**Independent Test**: Run `just flutter-test-golden` and see 3 component golden tests pass. Modify a component color, run again, see test fail. Run `just flutter-golden-update`, see new baselines generated.
**Prompt**: `/tasks/WP03-golden-test-examples.md`
**Estimated Prompt Size**: ~400 lines

**Requirements Refs**: FR-001, FR-002, FR-012

### Included Subtasks
- [x] T011 Write golden test for `MvButton` in `frontend/test/design_system/components/core/mv_button_golden_test.dart` — cover primary, secondary, and disabled variants; use `pumpWithGolden` helper; tag with `@Tags(['golden'])`
- [x] T012 [P] Write golden test for `RoleCard` in `frontend/test/design_system/components/game/role_card_golden_test.dart` — cover werewolf role, villager role, and face-down (hidden) states
- [x] T013 [P] Write golden test for `PlayerCircle` in `frontend/test/design_system/components/game/player_circle_golden_test.dart` — cover default, selected, and eliminated states
- [x] T014 Validate generate/compare/update cycle: generate baselines → verify test passes → modify widget appearance → verify test fails with diff → run `flutter-golden-update` → verify test passes again
- [x] T015 Validate determinism: run golden tests twice consecutively, compare baseline files byte-for-byte to confirm identical output

### Implementation Notes
- Each golden test file follows the pattern: `@Tags(['golden'])` annotation, `testGoldens('description', (tester) async { ... })` using the `pumpWithGolden` extension
- Baselines are generated on first run; subsequent runs compare against them
- T014 is a validation step, not a test file — document the procedure in a comment block at the top of one golden test file
- Use `MidnightVillageTheme()` (production theme) for golden baselines, not `TestThemeTokens` — goldens should match real appearance

### Parallel Opportunities
- T011, T012, T013 are fully independent (different components, different files)
- T014 and T015 depend on all golden tests being written first

### Dependencies
- Depends on WP01 (golden test helper, flutter_test_config.dart, justfile commands)

### Risks & Mitigations
- Platform rendering differences may cause CI failures even with deterministic fonts — this is why platform-specific baseline directories exist (WP01 T003)
- Some components may require provider overrides beyond what `pumpWithGolden` provides — extend the helper or compose with `pumpWithTokens` as needed

## Work Package WP04: Reusable Test Harnesses (Priority: P1) 🎯 MVP

**Goal**: Build builder-pattern test harnesses that reduce per-test setup to ≤5 lines for common scenarios: authenticated user, game phase state, and full-app bootstrap with mocks.
**Independent Test**: Write a widget test using `pumpAuthenticated` that renders a widget requiring auth state in 3-5 lines of setup. Write a test using `pumpWithGameState` that simulates a voting phase with 5 players.
**Prompt**: `/tasks/WP04-test-harnesses.md`
**Estimated Prompt Size**: ~450 lines

**Requirements Refs**: FR-007, FR-017

### Included Subtasks
- [x] T016 Create `frontend/test/helpers/pump_app.dart` — `pumpApp` extension on `WidgetTester` that boots the full `MidnightVillageApp` wrapped in `ProviderScope` with mock HTTP client, mock WebSocket, and configurable route overrides
- [x] T017 Create `frontend/test/helpers/test_harness.dart` — `pumpAuthenticated(widget)` extension that pre-loads auth providers (token storage, user state) with valid test credentials; `pumpWithGameState(widget, {required GamePhase phase, required List<Player> players})` extension for game scenarios
- [x] T018 Write harness-backed widget test in `frontend/test/helpers/examples/authenticated_harness_test.dart` — demonstrate authenticated state setup in ≤5 lines, render a widget that requires auth, assert on content
- [x] T019 Write harness-backed widget test in `frontend/test/helpers/examples/game_state_harness_test.dart` — configure voting phase with 5 players, render a game widget, assert on player names and phase indicator
- [x] T020 Write test in `frontend/test/helpers/examples/websocket_harness_test.dart` — use mock WebSocket via harness to emit a `phase_change` event, verify UI updates accordingly

### Implementation Notes
- Harnesses compose on top of `pumpWithTokens` (not replace it) — each extension calls `pumpWithTokens` internally and adds provider overrides
- `pumpAuthenticated` overrides: `tokenStorageProvider` → fake with valid JWT, `currentUserProvider` → test user object
- `pumpWithGameState` overrides: `gameStateProvider` → mock with configured phase/players, `webSocketProvider` → mock channel
- `pumpApp` is for integration-style widget tests that need the full app with routing — it combines all mock layers
- All harness extensions accept optional `overrides` parameter for test-specific customization

### Parallel Opportunities
- T016 and T017 can proceed in parallel (different files)
- T018, T019, T020 depend on T016/T017 but are independent of each other

### Dependencies
- Depends on WP01 (deterministic rendering foundation)
- Depends on WP02 (mock HTTP, mock WebSocket, timer control)

### Risks & Mitigations
- Provider override API may change with Riverpod 3.x — follow existing `pumpWithTokens` override pattern as the proven approach
- Game state types may not be defined in the frontend yet — create minimal placeholder types or use dynamic maps until real types exist

## Work Package WP06: Visual Diff Comparison Tooling (Priority: P2)

**Goal**: Build a Dart CLI tool that processes golden test failures to produce pixel-diff overlay images and an HTML comparison report for rapid triage of visual regressions.
**Independent Test**: Break a golden baseline, run the diff report tool, verify it produces side-by-side comparison and magenta-highlighted pixel overlay. Verify the HTML report lists all failures with thumbnails.
**Prompt**: `/tasks/WP06-visual-diff-tooling.md`
**Estimated Prompt Size**: ~450 lines

**Requirements Refs**: FR-014, FR-015

### Included Subtasks
- [x] T027 Create `frontend/tool/golden_diff_report.dart` — Dart CLI entry point that scans `test/` for golden test failure outputs (`.png` files in `failures/` directories), identifies baseline vs actual pairs
- [x] T028 Implement pixel-diff overlay generation: load baseline and actual images, produce a third image where unchanged pixels are dimmed (50% opacity) and changed pixels are highlighted in magenta (#FF00FF); save as `*_diff.png` alongside the pair
- [x] T029 Implement HTML comparison report: generate `golden_diff_report.html` with a summary table listing all failing components, side-by-side thumbnails (baseline / actual / diff overlay), and click-to-expand full-size views
- [x] T030 Add `flutter-golden-report` command to `frontend/justfile` — runs `dart run tool/golden_diff_report.dart`; add a combined `flutter-golden-check` command that runs golden tests and then generates the report if any failed
- [x] T031 Validate by deliberately breaking a golden baseline (change a color token), running `just flutter-test-golden` (expect failure), then `just flutter-golden-report`, and checking the output HTML and diff images

### Implementation Notes
- Use `dart:ui` or the `image` package for pixel-level image comparison and overlay generation
- The CLI tool reads from Flutter's golden test output directory structure (typically `test/failures/` or configurable via the custom comparator)
- HTML report should be self-contained (inline CSS, base64-encoded images) for easy sharing
- Consider adding a `--open` flag that launches the report in the default browser
- Bulk update (`flutter-golden-update`) already exists from WP01 — this WP adds the review/triage step before updating

### Parallel Opportunities
- T027 (CLI scaffold) and T028 (pixel diff) can be developed sequentially in the same file
- T029 (HTML report) can proceed once T028 is stable
- T030 (justfile) is independent

### Dependencies
- Depends on WP03 (golden test baselines must exist to have failure artifacts to process)

### Risks & Mitigations
- `dart:ui` may not be available in CLI context — use the `image` pub package instead for non-Flutter Dart scripts
- Golden test failure output directory location may vary by Flutter version — make the scan path configurable with sensible defaults

**Prompt**: `/tasks/WP07-ci-pipeline.md`
**Estimated Prompt Size**: ~350 lines

**Requirements Refs**: FR-010, FR-011

### Included Subtasks
- [ ] T032 Create or extend CI workflow file to run widget tests (`flutter test`), golden tests (`just flutter-test-golden`), and integration tests (`just flutter-test-integration`) as separate jobs/steps
- [ ] T033 Configure golden test failure artifact upload — on golden test failure, run `just flutter-golden-report` and upload the HTML report + diff images as build artifacts

- [ ] T035 Verify golden test platform consistency: generate baselines on Linux CI, confirm they match the `linux/` baseline directory; document the baseline generation workflow for contributors on macOS
- [ ] T036 Verify CI failure blocks merge: configure branch protection or CI status checks so that any test layer failure prevents merge

### Implementation Notes
- CI platform: check if the project uses GitHub Actions, GitLab CI, or another system — adapt the workflow accordingly
- Golden tests on Linux CI will use `linux/` baselines; macOS developers use `macos/` baselines — the custom comparator from WP01 handles this
- Integration tests on CI need Chrome headless — add `google-chrome-stable` or use a Flutter Docker image with Chrome
- Artifact upload: use platform-specific syntax (e.g., `actions/upload-artifact@v4` for GitHub Actions)
- Consider caching Flutter SDK and pub dependencies for CI speed

### Parallel Opportunities
- T032, T033, T034 can be developed in the same workflow file but address independent concerns

### Dependencies
- Depends on WP03 (golden tests to run in CI)
- Depends on WP05 (integration tests to run in CI)
- Depends on WP06 (golden diff report tool for artifact generation)

### Risks & Mitigations
- CI golden test rendering may differ from local even with deterministic fonts — this is the purpose of platform-specific baseline directories; ensure `linux/` baselines are committed by CI or a Linux contributor
- Chrome headless availability on CI runners — use a Flutter Docker image or install Chrome explicitly in the workflow
