## Tribal Knowledge

### Team Conventions

- **Server-authoritative:** ALL game logic runs on the server. Clients send actions, server validates and broadcasts. Never compute game logic client-side.
- **Hidden information:** API responses are player-scoped. A player only sees what their role allows. Never leak another player's secret info through API responses, WebSocket events, or error messages.
- **State machine:** Games have phases with explicitly defined valid transitions. Invalid transitions must be rejected.
- **Atomicity:** Game state changes are all-or-nothing. Use `@atomic` for state transitions. No partial updates.
- **Determinism:** Same inputs produce same outputs. All randomness is seeded and logged for replay/debugging.
- **Separate game apps:** `apps.core` has shared infrastructure (auth, lobbies, WebSockets). Each game type is its own Django app (`apps.onuw`). No premature abstraction across games.
- **Commit format:** `type(scope): description` — types: feat, fix, test, refactor, docs, chore
- **API errors:** `{"error": {"status_code": N, "detail": "..."}}`
- **URLs:** lowercase with hyphens, plural nouns for collections
- **HTTP for CRUD; WebSocket for anything requiring multi-client updates**

### Lessons Learned

- ONUW engine must be pure Python (no Django imports) for testability
- Keep game logic independent of HTTP layer
- Test multi-player scenarios, not just single player
- Doppelganger edge cases are the hardest — always consider role-copy chains
